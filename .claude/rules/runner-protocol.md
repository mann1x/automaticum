# Runner protocol conventions

- `const Protocol` in `internal/run/protocol.go` must equal `const PROTOCOL` in `runner/runner.mjs` (currently 8). Bump both together and describe the change in `runner/PROTOCOL.md` under its dated protocol entry.
- The lane image copies runner modules one by one: a new `runner/*.mjs` (for example `runner/guards.mjs`) must be added to the `COPY runner/...` line in `images/base/Dockerfile`, then `./bin/automaticum image build` before an end-to-end run.
- Every runner module has a test in `runner/test/<name>.test.mjs` (Node test runner); `runner/test/guards.test.mjs` pairs with `runner/guards.mjs`.
- A new field on the runner's last line (`End` in `internal/run/protocol.go`) that a harness rule depends on is a pointer or `json.RawMessage` with `omitempty`, so `nil` means an older runner did not report it and the old rule still holds. Add `run_test.go` rows for the new value, the old value and the field missing.
- A new run outcome (such as `guard_stop`) gets an `Outcome*` constant in `internal/run/protocol.go`, a verdict mapping in `internal/run/verdict.go`, a row in the outcome table of `runner/PROTOCOL.md` and its spec in `docs/specs/040-runner.md`.
- Guard trips are `notice` events of the SDK whose `metadata.kind` names the guard and `metadata.phase` what it did (for a `nudge`, `metadata.nudge`; for a guard that says what repeated, `metadata.cause`, carried as `cause` on the runner's `guard_trip` and `guard_stop` notes); `GUARD_KINDS` in `runner/guards.mjs` and `guardPhases` in `internal/config/arm.go` hold the same table and change together. Never invent a guard kind, phase, cause or threshold: confirm it in the installed SDK build or on the stub.
- A new arm setting under `[guards]` or `[thinking]` (such as `stop_on`, `reasoning_history`, `reasoning_inline`, `guards.reasoning_loop.max_consecutive_trips`) is stated in `arms/base.toml` and required by `need(...)` in `internal/config/arm.go`; its neutral value (empty, false, or the SDK's own default such as `reasoning_history = "auto"` with `reasoning_inline = true`, or `max_consecutive_trips = 3`, `sdkReasoningLoopTrips`) is dropped from `Arm.Resolved()` so older arms keep their identity, and `internal/config/config_test.go` proves it. Run behaviour the owner chooses (which guards stop a run, how much earlier reasoning goes back in the history) is arm configuration, never runner code: a `stop_on` selector is a guard or `guard.phase`, validated against `guardPhases` by `Arm.Validate()` and matched by `stopsOn` in `runner/guards.mjs`; `thinking.reasoning_history` is one of `auto`, `all`, `last`, `none` (`histories` in `internal/config/arm.go`).
- At the reasoning-loop limit (D108, protocol 8) the runner answers the SDK's `onReasoningLoopLimitReached` from `stop_on` alone (`reasoningLimitAnswer` in `runner/guards.mjs`: `stop` only if it names `reasoning_loop` or `reasoning_loop.aborted`) and notes `guard_limit`; an SDK that ends the run anyway, or after another number of cut turns than the arm states, or (4.100.266 on) whose `cut`/`aborted` notice reports a `maxConsecutiveTrips` other than the arm's, makes the run `invalid` (`limitBreach`, note `guard_limit_breach`, noted once per reason).
- The runner hands arm settings the SDK reads from its provider configuration (`reasoningHistory`, `reasoningInline`, the sampler) to `providerConfig` in `buildConfig` of `runner/session.mjs`; a stated value the runner would otherwise ignore is a protocol bump (protocol 6, D103). Confirm the SDK field names in the installed build, never from memory.
- `compareResolved` in `runner/session.mjs` reads back `thinking.reasoning_history` from `resolved.reasoningHistory.setting` only when the SDK reports it (release 4.100.260 on, `runner/sdk/4.100.260/sdk.toml`); what `auto` resolved to is recorded, never compared. A read-back of a setting an older SDK does not report must stay silent on that build, with a case in `runner/test/session.test.mjs`.
- Metrics derived from a new runner note (`guard_trips`, `guard_trips.<guard>.<phase>.<cause>`, `guard_stop.*`) are counted in `internal/ingest/events.go`, emitted in `Analyse` in `internal/ingest/analyse.go` beside the existing totals (never instead of them), and hidden at zero in `cmd/automaticum/client_cmds.go` like the `user.` and `mode_switches.` metrics. A new metric bumps `AnalysisVersion` in `internal/ingest/analyse.go` (now 6) and gets a dated "From analysis version N" note in `docs/specs/070-diagnostics.md` section 2.
- `Events.Read` in `internal/ingest/events.go` creates its count maps (`Notices`, `GuardTrips`, `GuardCauses`) when they are nil: the daemon's detect view starts from a bare `Events{}` (bug-031). A new counted map must be added there and proved by a bare-`Events` case in `TestGuardTrips` in `internal/ingest/ingest_test.go`.
- A per-batch option that changes nothing on the wire (the request capture, D104) is not an arm setting: it is a `StartRequest` field in `internal/daemon/api.go` (`CaptureRequests`, flag `-capture-requests` of `automaticum run start`), kept by batch in the daemon's control file (`control.Capture` in `internal/daemon/control.go`) so a restarted daemon still knows, handed to `run.Request` and written to the job as `save_model_requests` (protocol 7). The runner passes it as the SDK's `saveModelRequests` (4.100.261 on; an older SDK writes nothing) under `requests/` in its output, which `kindOf` in `internal/run/run.go` keeps as the `model_requests` blob. Off by default: never widen an opt-in into a default.
