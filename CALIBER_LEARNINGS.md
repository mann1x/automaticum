# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** `caliber init --agent claude --auto-approve` runs non-interactively and exits 0. It takes about a minute or more, so run it in the background and check the result afterwards. `--auto-approve` is valid for `init` only, not for `caliber refresh`.
- **[env]** GitHub repos for this project go under the `mann1x` account (`gh repo create mann1x/<name> --public --source . --remote origin`), which differs from the local git user name.
- **[pattern]** Other AI sessions send inputs through the pgvector mailbox. The tools are deferred: load them with ToolSearch (`select:mcp__pgvector__mailbox-list,mcp__pgvector__mailbox-read,mcp__pgvector__mailbox-ack`). When the owner says a mail is coming, poll `mailbox-list` between work steps and do not block on it.
- **[gotcha]** Another session may drop uncommitted files into this working tree (a new spec under `docs/specs/`, plus lines in `README.md`, `.wolf/anatomy.md` and `.wolf/memory.md`). Run `git status --short` and read the mail before staging, and do not overwrite those edits.
- **[convention]** The legacy harness, its run corpus and the Cerebriline checkout (locations in `docs/local/hosts.local.md`) are read-only. Survey them with read-only commands, and say so explicitly in any sub-agent prompt ("modify nothing, build nothing").
- **[gotcha]** In the Cerebriline checkout there is no `@cerebriline/*` source directory. The packages are `@cline/*` under `sdk/packages/` and the scope is rewritten only at pack time, so grep for `@cline/` or `ClineCore`. `npm view @cerebriline/sdk version` gives the published version.
- **[gotcha]** Legacy run streams (`run.jsonl`, `TX-*.jsonl`) range from a few MB to several GB. Never `cat` or Read them. Summarise them with a streaming script (`python3 -I` counting event types and keys) or `zcat | head`.
- **[pattern]** For broad read-only surveys, launch parallel `Explore` sub-agents. Give each a numbered list of questions, a word limit, "facts only", and "state what you could not verify". Keep working on other things while they run.
- **[pattern]** Put open spec questions to the owner in batches of up to four with `AskUserQuestion`, each with a recommended option first and the trade-off of every option in its description. Then read the returned answers one by one: the owner does not always take the recommendation, and may type an answer that is not among the options (e.g. "C/C++ first" where the recommendation was C#).
- **[convention]** When an owner answer conflicts with an earlier one or is ambiguous (C# named primary, then not ticked in the language multi-select), do not silently pick a reading. Record the reading you chose as a note under the decision table in `docs/specs/decisions.md` (as for D15), repeat it in `.wolf/cerebrum.md`, and say what would change if the other reading was meant.
- **[convention]** `docs/specs/decisions.md` has more than the `D`, `O` and `X` ids. Choices you made yourself while drafting go in section 2 as `S` rows ("settled in the planning session", can be overturned), never as `D` rows. Alternatives from an input document that were rejected go in section 5 with the `D` or `S` id that rejected them. Something the owner called a preference pending a spike is written as "Owner's preference", not "Decided".
- **[gotcha]** `grep -n -F '**Open' docs/specs/*.md` also matches the prose sentence in the Status paragraph of `000-overview.md`, and one Open row (the milestone order as a whole) has no inline marker. Equal counts of grep hits and `O` rows therefore prove nothing: check each marker against its `O` row by file and section.
- **[pattern]** After renaming, moving or splitting a spec file, grep for the old name in `README.md`, `CLAUDE.md`, `.claude/rules/` and every `.claude/skills/*/SKILL.md` (`grep -rn '<old-name>' --include=*.md . --exclude-dir=.git`). Skill descriptions and their `paths:` front matter embed spec paths and go stale. Then run a relative-link check over `README.md` and `docs/specs/*.md`; it must report 0 broken links.
- **[gotcha]** `CALIBER_LEARNINGS.md` quotes the private-string grep pattern, so it always matches the pre-commit scan for `/srv/` and `/shared/`. Exclude it from the scan (`git ls-files | grep -v CALIBER_LEARNINGS.md | xargs grep ...`) and check it separately for nicknames only.
- **[gotcha]** The Caliber pre-commit hook writes `CALIBER_LEARNINGS.md` (and `.wolf/memory.md` gets appended) during the commit itself, so they can be left untracked or modified right after a commit. Run `git status --short` after committing and before pushing, and stage what the hook left behind in the next commit.
- **[convention]** A spec that states facts taken from reading another project's source or from a survey says so in its `**Status:**` line (which release was read, "not verified by running it", survey date), and anything needed from that project becomes a numbered request in the spec plus an `X` row in `decisions.md`. Sub-agent reports contain absolute paths: strip them before copying findings into a tracked file.
- **[correction]** Never put store data, spike data, build caches or third-party clones on the development NVMe (filling it blocks every project) or on the old harness's spool NVMe (heavily used), even when `df` shows free space there. Live data, indexes and caches go on the dedicated disk recorded in `docs/local/hosts.local.md`, and the archive tier goes on the large array. Do not recommend the development disk as a data root.
- **[pattern]** "chk mail" from the owner means: `mailbox-list`, `mailbox-read`, apply the content to the specs, then `mailbox-ack` each mail with a note saying what was applied, in which draft and commit, and what is still awaited from the sender. Start new threads with `mailbox-send` (load it with ToolSearch as well). Do not stop background work to do this.
- **[convention]** When owner answers close Open items, do all of this in one pass: replace the inline `**Open**` marker with `**Decided by the owner (YYYY-MM-DD):**`, add the `D` row, delete the `O` row and name it in the "Closed since" line of `decisions.md` section 3, bump that file's revision number and each touched spec's draft number, and add a dated line to `.wolf/cerebrum.md`. If a new decision overrides part of an older one, say so in the new row ("supersedes the ... part of D7"). Anything you added beyond the owner's answer (e.g. a build order) is labelled a proposal in the text.
- **[convention]** An `X` request to another project has its status in two places: the spec that makes the request (`040-runner.md` section 8) and `decisions.md` section 4. Update both together. When the other session reports the work done, record exactly what it reported: "on main, unreleased" is not "landed", and list what was only partly covered and what that session said it did not test.
- **[convention]** The "spec stage, no `go.mod`" lines in `CLAUDE.md` are out of date since 2026-10-12: the owner approved the roadmap and milestone 1 (store spike and legacy importer, D28, D29), and `go.mod` (`github.com/mann1x/automaticum`), `LICENSE` (Apache-2.0), `Makefile`, `build/Dockerfile.build` and `spike/001-store/` exist. Code is still written only inside a milestone plan the owner has approved; check `110-acceptance-and-roadmap.md` section 3 and `decisions.md` before adding packages.
- **[env]** Native (cgo, Rust) builds run only inside the `automaticum-build:deb11` container (`make image`, then `make shell SPIKE_ROOT=<dir>`); install no toolchain on the host. `SPIKE_ROOT` and the other local paths come from the untracked `spike.local.toml` and `docs/local/hosts.local.md`, never from a tracked file. The oldest host has glibc 2.31, so check any prebuilt native library before relying on it (`objdump -T lib.so | grep -o 'GLIBC_[0-9.]*' | sort -V | tail -1`) and build from source in the container when it needs a newer glibc.
- **[fix]** In a `debian:11` image, `apt-get install` fails with exit code 100 and 404s on `bullseye-security` packages from `deb.debian.org`. Point `/etc/apt/sources.list` at `archive.debian.org` (`debian` and `debian-security`) and set `Acquire::Check-Valid-Until "false"`, as `build/Dockerfile.build` does. `docker build -q` hides the cause: rerun with `--progress=plain 2>&1 | grep -E 'Err:|E: |404'`.
- **[env]** Native (cgo, Rust) builds run only in containers; install no toolchain on the host. There are two images since 2026-10-12: `build/Dockerfile.build` is `manylinux_2_28` (glibc 2.28, GCC 14; tags `automaticum-build:ml228-amd64` and `automaticum-build:ml228-arm64`) and does every final cgo link; `build/Dockerfile.cross` is Debian 11 (tag `automaticum-build:deb11`) and only cross-compiles the Rust static archives. `SPIKE_ROOT` and the other local paths come from the untracked `spike.local.toml` and `docs/local/hosts.local.md`, never from a tracked file. The oldest host has glibc 2.31, so check any binary or prebuilt library before relying on it (`objdump -T <file> | grep -o 'GLIBC_[0-9.]*' | sort -V | tail -1`).
- **[fix]** Linking the prebuilt DuckDB static archive (`duckdb-go-bindings`) with Debian 11's GCC 10 fails with hundreds of ``undefined reference to `std::__throw_bad_array_new_length()'``. Do the `go build` in the `manylinux_2_28` image instead; the result needs only glibc 2.28 and runs on the Debian 11 host. Rust archives compiled in the `deb11` image link cleanly there.
- **[gotcha]** Both build images carry two Rust toolchains. The default (1.89) builds `lancedb-go`; `lance-c` fails on it with a long list of `requires rustc 1.91` lines and must be built with `cargo +1.99.0 build ...`. Name the toolchain explicitly in every `lance-c` build command.
- **[gotcha]** A background build whose command ends in `| grep ... | tail` or `; ls ...; date` reports "completed (exit code 0)" even when cargo or `go build` failed. Never trust the task notification: read the log and test that the artifact exists (`[ -f .../release/lib*.a ]`) before the next step. Inside the container, capture `rc=$?` straight after `go build > log 2>&1` and print `BUILD FAILED` on non-zero.
- **[gotcha]** A foreground Bash call is moved to the background after 10 minutes whatever `timeout` is passed, and returns empty output. An arm64 final link under emulation takes 7 to 8 minutes (1 minute native on amd64), and a Rust archive build 6 to 12 minutes: start these with `run_in_background` and read the log when notified.
- **[pattern]** Run native builds one at a time: they share the cargo target directory and all cores. Queue the next one behind the running container with `( docker wait <container-name>; docker run --rm --name <next> ... ) &`, give every build container a `--name`, and write each log to its own file under `$SPIKE_ROOT/work/` (not `/tmp`). Use a separate Go build cache directory per image and architecture, mount the Rust target directory read-only for link steps, and set `GOFLAGS=-buildvcs=false` when the repo is mounted into the container.
- **[gotcha]** Do not spend time on these again without a new reason; both were tried on 2026-10-12 and are recorded in `spike/001-store/linkcheck/README.md`. A fully static link (`-extldflags "-static"`) fails in the manylinux image because it has no static glibc, and `-static-libstdc++` changes nothing because DuckDB's link flags name the shared C++ runtime. A Windows amd64 link with Debian 11's MinGW (GCC 10, win32 thread model) fails on `pthread_mutex_*` and `std::__throw_bad_array_new_length` references from the DuckDB archive; Windows is not required for the store (D40).
