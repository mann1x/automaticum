- **[correction]** A recommendation on an Open item is not the owner's answer, and a rule that makes a run `INVALID` gets an override for the arm that tests exactly that condition: on O21 (does a model loaded again mid-run, or a model partly off the GPU, invalidate the run) the recommendation was a flat `INVALID`, and the owner answered "Not necessarily. I may want to test exactly that use case. default INVALID, with override" (D73). As built: `[accepts] model_reload = true` and `partial_gpu = true` in an arm (030 §5.3), each false when left out; without them ingest sets the run `INVALID` with a reason starting `endpoint: `, keeps the verdict it had as the prior verdict and writes the finding with severity `error`; with them the run keeps its verdict, the finding is a `note`, and gate `gpu_residency` lets the run start with the model partly on the GPU. Because the rule sits in ingest, `automaticum reanalyse` applies it to earlier runs and takes back an `INVALID` it set itself once the cause is gone; it never touches an `INVALID` an operator set with `run invalidate`. When proposing any rule that refuses or invalidates a run, propose the override with it.
- **[convention]** A new optional section or field of an arm must leave the identity of every existing arm unchanged, since the identity is the hash of the resolved JSON: give the struct field `json:"...,omitzero"` and its members `omitempty`, so an arm that does not state it resolves to the same bytes. - **[correction]** An improvement does not mean reworking what was done: when the reference code of a detector turned out to have a blind spot (it looks only at the first repeat in a block), the owner chose the corrected behaviour as the reference, said that loop rates already published stay as published ("it wouldn't be practical and stop progress"), and called it important to be able to tell which detector produced a number (D76). - **[correction]** A report or comparison gives the reader every statistic and draws no conclusion (D78): a plan to label two arms "distinguishable" was met with "difference of what?", and the owner said that with small models the swing from run to run is very large, the history of earlier runs is what has told noise from a real difference, and the best that can be done for now is to give all the statistics. - **[pattern]** Pause inside a run (D77) is no longer waiting on the SDK: its session answered on 2026-10-13, from a reading of tag `v4.100.251` and not a test, that there is no pause call for the root session (`abort` cuts mid-generation, `stop` cannot be resumed) but the agent runtime awaits `hooks.beforeModel` before every model request, so a hook that waits holds the run between two requests, never mid-stream, and the same process goes on with the request already built. - **[pattern]** A rebuilt `bin/automaticumd` is not the daemon that is running: after `make build`, check that it is idle (`automaticum status`), find it by its port (`ss -ltnpH 'sport = :7411'`, which gives the pid), send `kill -TERM`, wait in a bounded loop until `kill -0 <pid>` fails, start the new binary with `nohup ... >> <work>/automaticumd.log 2>&1 &`, and wait until `curl -sf http://127.0.0.1:7411/v1/status` answers before the next command; the log then shows `detector self-test passed` before `automaticumd is up`. The files of `runner/` are copied into the lane image, so a change there is live only after `automaticum image build` (check with `automaticum image ls`); like the daemon restart, do it only with the lane idle and the queue empty, never while a batch runs (it would split the batch or abort its run): write and unit-test meanwhile, deploy after.
