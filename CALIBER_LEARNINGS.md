# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[gotcha]** Before a batch on a new llama-server endpoint, do not trust `/props` `default_generation_settings.params.chat_format` and `reasoning_format`: they read `Content-only` and `none` even when tool parsing and the reasoning channel work, because they are the idle defaults, not what a chat request gets. The evidence is a run's `tool_calls` and `thinking.blocks`. Have the server owner confirm the GGUF is the instruct file (`general.name` ending `-it`) and curl one tools + thinking request first: a base model served by mistake answers off-task text with no tool calls and no reasoning, and the run FAILs in seconds. If the first run shows 0 tool calls and `thinking.blocks 0`, pause the batch and mail the server owner instead of letting it run.
- **[pattern]** To learn what the Cerebriline SDK really does, read the installed build under `<data_root>/sdk/<release>/node_modules/@cerebriline/` on the host that runs the lane (the lane image holds only the runner under `/opt/automaticum`, not the SDK). `data_root` is in the config's `automaticum.toml`, and `automaticum sdk ls` lists the builds. Grep the `.d.ts` files in `core/dist`, `shared/dist` and `agents/dist` for types (`shared/dist/agents/types.d.ts` has the event shapes, `core/dist/runtime/safety/` the guards). For the logic read `core/dist/index.js` or `agents/dist/index.js`; `core/dist/hub/daemon/entry.js` repeats core's code and is what `grep -rl` finds first. The provider layer (the provider list as `id:"<name>",name:`, the effort-to-budget table, the reasoning-history scope per provider) is in `llms/dist/index.js`. `grep` here is ugrep and rejects some patterns as too complex: `.{0,N}` with alternation, large bounded classes, and `-o '.\{300\}needle.\{500\}'` returns nothing; `-o "[^;]\{0,250\}needle[^;]\{0,250\}"` on a minified bundle runs past two minutes. For a window around a needle use `python3 -c` with `re.finditer(re.escape(needle), s)` and print `s[m.start()-500:m.start()+700]`. Never guess SDK behaviour; confirm it there or on the stub.
- **[gotcha]** With the `openai-compatible` (and `opencoti`) provider, `[thinking] owner = "arm"`, `enabled = true` without an effort puts nothing on the wire. An effort is sent as `reasoning_budget_tokens`, a share of the output limit (`max_tokens`): max 4/5, high 1/2, medium 1/4, low 1/8, minimal 1/16; a numeric `budget_tokens` is sent as is and `enabled = false` sends 0. wire_arm (version 3) reads it as `options.think_budget_tokens` and takes a positive budget on an OpenAI-style request as the arm's effort sent. `thinking.blocks` in `run show` tells whether the model thought. Check what reached the server with the first line of `logs -wire <id>`: decode `request_body` and drop `messages` and `tools`.
- **[correction]** The Gemma-4 loop arms state thinking on the arm, `[thinking] owner = "arm"`, `enabled = true`, `effort = "high"`, not left to the server's template (owner: "we set High thinking budget on the arm"). The server's own `--reasoning-budget -1` and `enable_thinking` template flag say nothing about the budget the SDK sends; only the arm's effort does.
- **[gotcha]** `automaticum run tail <id>` works only on a run in flight and never ends; on a finished run it prints only a hint. `automaticum logs <id>` on a run in flight answers `has no events`: the streams reach the store when the run ends. While it runs, the live capture is `<data_root>/runs/<id>/out/wire.jsonl` on the lane's host; read it there (rows with `chat/completions` in `url`, `request_body` and `response_body` as JSON strings) and check the first request's sampler and provider fields within a minute of `run start`, before telling anyone the batch is right. Capture a live tail with a bound to persistent disk: `timeout 8 ./bin/automaticum run tail <id> > <work>/tail.jsonl; true`. Read a finished run with `timeout 60 ./bin/automaticum logs <id>`, its wire with `logs -wire <id>` (there is no `-kind wire`). Wire lines are flat; some have no body or an `error` field, so read with `d.get(...)`. In `logs`, an SDK event is nested as `event.payload.event` (the agent's `type`, `noticeType`, `metadata` live there). `run ls` takes `-limit N` (default 30), not `-n`.
- **[correction]** A sampler relayed by a peer session as "the owner's serving config" may be the config for the opposite condition: the "8244" values (temperature 0.7, repeat penalty 1.13 over 72, presence 0.25) were the owner's anti-loop sampler, so the Gemma-4 loop test measured the fix (owner: "these are the sampling parameters to avoid looping!"). Ask the owner for the exact sampler of the condition under test and show it with `arm show` before the first run. The owner's loop sampler is temperature 1.0, top_p 0.95, top_k 64, min_p 0, repeat_penalty 1, repeat_last_n 0, presence_penalty 0; state the zeros in the arm so the server's defaults (min_p 0.05, repeat_last_n 64) do not apply. Batches run on a wrong sampler, provider or thinking setting are another arm: `batch stop` them, `run abort` the one in flight, and never pool them with the corrected runs.
- **[correction]** The Gemma-4 loop test loops within minutes. A run of short-reasoning tool-call turns that passes the oracle in 12-16 min means the arm is wrong (sampler, provider or thinking), not that the guards work: the owner's words were "if it's not looping something is wrong". Stop the batch, read the wire and ask before reporting numbers or mailing the server owner.
- **[correction]** An endpoint that is an opencoti (or xollama) server gets the SDK provider of that name in `model.provider`, never `openai-compatible` (owner: "why openai-compatible? cerebriline has opencoti provider"). The providers differ in what goes back to the server: for `opencoti`, `ollama`, `xollama` and `cerebras` the SDK's reasoning-history scope is `none`, for `openai-compatible` it is `all` (the model's reasoning is re-sent in every request), so the provider changes what the model sees and whether it loops. `arm validate` does not check `model.provider` against the SDK's list, so read the provider list in `llms/dist/index.js` yourself before writing an arm. Record such a change as a new D row in `docs/specs/decisions.md` with the revision bumped, and say in the arm's comment that the earlier runs are another arm.
- **[pattern]** Inline Python through `ssh <host> 'python3 - <<EOF ... EOF'` with nested quotes comes back empty with no error, and so does a quoted `ps | grep` pipeline. Write the script on the local scratch, `scp` it to the host's persistent work directory (never its `/tmp`) and run `ssh <host> 'python3 <work>/<script>.py <file>'`.
- **[pattern]** To see what a model server on a port was started with, find the pid with `ss -ltnpH "sport = :<port>"` and read `tr "\\0" " " < /proc/<pid>/cmdline`. An opencoti server is an `.ape` binary, so grepping `ps` for `llama-server` finds nothing. Its flags (`--chat-template-kwargs`, `--reasoning-format`, `--reasoning-budget`, `-a <alias>`) are what the template gets; `/props` does not show them, and `claude-hooks-res status | grep <host>` says which session holds the GPU it runs on.
- **[gotcha]** A batch id is not the run ids' prefix (runs `...-819b65-NNN` belonged to batch `b...-524ef9`), and `batch pause` with the prefix answers `has no run queued or in flight`. Take the batch id from the first line `run start` prints (`... batch b<id>`) or from `run show -json <run>` field `batch`. `batch pause` holds the in-flight run before its next model request: the run stays `running` and the lane stays busy until `run abort <id>`; the "endpoint freed of its model" part applies to Ollama-kind endpoints only, a llama-server endpoint is never unloaded. `batch stop` records every queued run `SKIPPED` and lets the in-flight one finish (`finishes, then the batch is over`), so `run abort <id>` it as well; `ABORTED` shows in `run ls` after about 20 s.

- **[pattern]** When you add a required arm setting (030 §5.1: every guard setting must be stated), make it a pointer (or a string) with `omitempty`, `need(...)` it in validation, add it to the list in `TestNothingIsDefaulted`, and drop its neutral value (false, an empty list, or the pair the SDK uses unasked, e.g. `reasoning_history = "auto"` with `reasoning_inline = true`) in `Arm.Resolved()`, so arms resolved before the field existed keep their id. Prove it: compare `run ls -json` `arm_id` prefixes of past runs with `arm show <arm>` ids. The old `bin/automaticum` refuses the edited `arms/base.toml` with `unknown fields: thinking.<new> (from base)`, so build a fresh pure-Go CLI to scratch (`CGO_ENABLED=0 go build -o <scratch>/am ./cmd/automaticum`) and validate with that until you rebuild. When renaming or replacing an arm setting, grep the old name with `--include=*.go --include=*.toml --include=*.mjs --include=*.md`: `.claude/rules/runner-protocol.md` and the specs (020, 030, 040, 070) reference arm fields too.
- **[gotcha]** In `internal/config/config_test.go` the `good` fixture already has a `[thinking]` table (and `[model]`, `[sampler]`), so `good + "[thinking]\n..."` fails with `toml: Key 'thinking' has already been defined`; insert the new key with `strings.Replace(good, "[thinking]\n", "[thinking]\n<key> = <v>\n", 1)`. Appending works only for tables `good` lacks (`[guards]`, as in `TestStopOnIdentity`). Substring checks on `Resolved()` must name the full key: `"reasoning_"` also matches `guards.reasoning_loop` and `guards.reasoning_repetition`.
- **[gotcha]** From SDK 4.100.259 every guard announces its action as a `notice` with `metadata.kind` (`loop_detection`, `reasoning_loop`, `tool_intent_overrun`, `nudge`, `edit_verification`, `checklist_close_out`, `team_obligation`, `struggle`) and `metadata.phase`; a nudge's phase is `metadata.nudge`. `reasoning_loop`, `tool_intent_overrun` and the nudge emitter are in `agents/dist/index.js`; `loop_detection`, the completion guards and `struggle` are in `core/dist/index.js`, so grep both with `grep -oE 'kind:"(<kinds>)"[^}]{0,120}'`. To trip `loop_detection` on the stub, a script with three or more identical `tool_calls` turns is enough; soft fires from the third and keeps firing on every repeat, and `edit_verification.nudge` shows up at completion too.
- **[correction]** Every reasoning setting the Cline plugin exposes is an arm setting with the plugin's default, stated in `arms/base.toml`: "Prior reasoning" is `thinking.reasoning_history` (`auto`, `all`, `last`, `none`) and "Inline thinking when the template drops it" is `thinking.reasoning_inline` (D103); the base states `auto` and `true` because the owner said "the provider default MUST BE auto like with the plugin". When you find an SDK setting the plugin has and no arm states, add the field, bump the runner protocol and mail the SDK's session; do not just report it. The SDK reads these from `providerConfig.reasoningHistory` / `reasoningInline` (the zod schema in `core/dist/index.js` lists the enum), so the runner must send a `providerConfig` even when the sampler is the tag's, and the SDK drops a `providerConfig` whose `providerId` is not the session's own.
- **[correction]** "The provider leaves reasoning out of the history" is not "the run has no reasoning". The owner's reaction to that phrasing: "what are you talking about? of course it has! it has both reasoning effort and budget!!". Say precisely which of the two you mean: the model thinks on every turn (effort or budget on the request, `reasoning_content` in every response, `thinking.blocks` in `run show`), while the assistant messages the SDK sends back may carry only `content` and `tool_calls`. Before stating either to the owner or a peer session, count assistant messages with `reasoning_content` in the last request on the wire.
- **[gotcha]** SDK 4.100.259, `reasoningHistory` unset or `auto`: for `opencoti` the SDK measures the template with a reinjection probe (`CLINE-REINJECTION-PROBE-8F2A`) POSTed to `${baseUrl}/apply-template`, which with a `/v1` base URL is `/v1/apply-template` and answers 404 (the server serves `/apply-template` at its root). After the 404 the scope falls back to the provider default: `none` for `opencoti`, `ollama`, `xollama`, `cerebras`; `all` for `openai-compatible`, which is never probed at all. So `auto` on an opencoti endpoint sends no prior reasoning and nothing tells the host. The evidence is a `/v1/apply-template` 404 row in the first rows of `wire.jsonl`. The scope and probe logic (`Op`, `WT`, `Fl`, `kt.set` in that build) live in `llms/dist/index.js`; reported to the SDK's session on 2026-10-23.
