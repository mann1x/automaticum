# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** To probe the SDK's exports or one tool alone inside a lane image, bind-mount the probe script at `/opt/automaticum/runner/<probe>.mjs`, next to the mounted `node_modules`. Placed anywhere else, `import * as sdk from "@cerebriline/sdk"` does not resolve, and importing the bundle by file path (`/n/@cerebriline/sdk/dist/index.js`) fails with `ERR_MODULE_NOT_FOUND ... @cerebriline/core`. For a quick `node --input-type=module -e` check, mount the build root (`<data_root>/sdk/<ver>`, which holds `node_modules`) with `--network none -v <build>:/s:ro -w /s` and import by package name. Anything that starts Chrome (the browser, `render_image`, `transform_image`) also needs `-e HOME=/tmp --tmpfs /tmp:exec` with `--user 1000:1000`. Print the tools' input schemas this way (`sdk.BROWSER_TOOL_INPUT_SCHEMA` etc.) before you write stub turns, rather than guessing argument names.
- **[pattern]** To read an SDK function's real implementation in the minified bundle (`<node_modules>/@cerebriline/core/dist/index.js`), find its local name from the export list with the regex `(\w+) as createEditorDiagnosticsHooks\b`. The export is written `Kmt as createEditorDiagnosticsHooks`, so `createX as (\w+)` finds nothing. Then print from `s.find('function ' + name + '(')`. The type declarations under `dist/extensions/**/*.d.ts` (`grep -rl <name> --include=*.d.ts`) give the option names to pass.
- **[pattern]** To see what really changed between two SDK releases (a dependency-only release, say), diff the installed bundles, not the source. For each of `@cerebriline/{agents,core,shared,llms,sdk}/dist` in the two builds, first compare the files byte for byte after replacing the old version string with the new one. Then diff only the changed `.js` files, with `difflib.SequenceMatcher` on token lists split after `;`, `{` and `}` (`re.split(r'(?<=[;{}])', s)`). A character-level SequenceMatcher on the minified bundles ran for over 10 minutes and had to be stopped. Every release also changes core's embedded package.json, its `sdk-v1-<hash>` build key and a build timestamp; those are not code changes. Then import both builds offline and compare the export count and the exports the runner needs (`createLspHost`, `createDiagnosticsCheckFileTool`, `createEditorDiagnosticsHooks`, `createChromeBrowserDriver`, `createChromeRenderDriver`). If agents and shared are byte-identical and core changes no guard code, map the release onto the existing `CallGuard`/rules version in the `callguard_test.go` release map. Do not bump the library version.
- **[convention]** Dependabot alerts on the repo are almost all in `runner/sdk/<ver>/package-lock.json`, the SDK's own dependency tree. Never bump them in our lockfile: that changes the SDK build and its `bundle_sha256`. Instead, mail the SDK owner the packages, GHSA ids and fixed versions for their next release. Keep the alerts on the current pins open, and dismiss the older pins' alerts as `tolerable_risk` with a comment. `tasks/tbench2/*/oracle/requirements.txt` is the pinned scorer and is never edited (dismiss as `tolerable_risk`); `spike/` modules are never built (`not_used`); `images/lsp` alerts come from upstream exact pins (check `registry.npmjs.org/<pkg>/latest` before calling one fixable). Fetch alerts with `gh api -X GET 'repos/<owner>/<repo>/dependabot/alerts?state=open&per_page=100' --paginate --jq '.[] | [.number, .dependency.manifest_path, ...] | @tsv'`; without `--jq`, `--paginate` concatenates JSON arrays and the output is not one valid document. Dismiss with `gh api -X PATCH .../dependabot/alerts/<n> -f state=dismissed -f dismissed_reason=<r> -f dismissed_comment=<c>` (comment under 280 characters). Test it on one alert and read it back, then run the rest as a background script with a short sleep between calls, using a `case` on the manifest path that skips the current pins.

End such commands with `; true`, or print the count with `echo`.
- **[gotcha]** In the private-name scan, `git ls-files -z | xargs -0 grep -Il ...` exits with **123** when nothing matches, not 1, because xargs reports 123 when any grep call returned 1. So `rc=123` on the tracked-files grep means clean. A pipeline that ends in `cut`, `head` or `tail` reports that command's status. Simplest: use `grep -c -i -E "$P"` and read the count (0 = clean), on `git diff --cached | grep '^+' | grep -v 'registry.npmjs.org'` before the commit and on `git show HEAD` after it. The `/shared/` pattern also catches prose that names the shared package followed by a slash and a path (its `dist` directory, for example), lists packages joined by slashes, or gives a source path that runs past `packages/shared`. Write "the shared package's dist/index.js" or "agents, shared and llms" instead. A hit in `CALIBER_LEARNINGS.md` after the commit hook has run needs `sed` plus `git commit --amend --no-edit --no-verify`. Absolute paths in Go test fixtures that look like host paths also hit the scan, so use neutral ones such as `/data/a` or `/opt/r`. `.wolf/memory.md` and `.wolf/buglog.json` are tracked, so their rows must use the neutral host names too: write "the blackswan-2 build claim", never the private resource name of a claim or GPU, and "the same artefact as the dev build", never the dev machine's name.
