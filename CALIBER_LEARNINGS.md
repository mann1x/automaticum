- **[gotcha]** If you edit Go source with `python3 - <<'EOF'` and a plain `'''...'''` string, a Go escape written as `\n` becomes a real newline in the file. That splits the Go string literal, and the next `go vet` fails with no clear message. Write `\\n` inside the Python string, or use `r'''...'''`. Existing struct fields are gofmt-aligned with runs of spaces (`allMetrics, noMetrics` followed by many spaces, then `bool`), so an exact `assert old in s` on a field line fails. Check the real line with `grep -n ... | cat -A` and match it with a regex that allows ` +` between name and type. If a script asserts partway, its own file is not written, but edits made by earlier steps (for example callers rewritten to use a variable the failed step was to add) are, so run `go vet` to see what state you are in. Run `gofmt -l` right after each scripted edit, and look at broken lines with `sed -n A,Bp file | cat -A`. Adding fields to a struct changes gofmt's field alignment, so `gofmt -l` listing the file after a scripted edit usually just means it needs `gofmt -w`. When you append a test with `cat >> file_test.go <<'EOF'`, check its imports first (`head -30 file_test.go | grep '"slices"'`); an import added with `sed` lands out of order, so run `gofmt -w` on the file afterwards.
- **[correction]** Keep `.wolf/memory.md` to actions that did something (owner, 2026-11-09). Never append a row for a monitoring or mail tick that changed nothing ("no mail, nothing to do", "waiting"). Log a tick only when it acted: a deploy, a mail answered, a failure found. The post-write hook also adds a new `## Session:` header and one `Created <file>` row per file you create, and empty session headers come back after every commit. Before every commit, run `git diff HEAD --numstat .wolf/memory.md`. - **[correction]** A task version bump is not automatically a comparability boundary (owner, 2026-11-12: "why v4 and v5 should not be comparable? don't be silly, the v4 runs can be validated with the same v5 oracle"). - **[pattern]** After any change to a task's oracle source, seed or `task.toml`, do these steps. Bump `version`: what the agent reads changed (whether it is also a comparability boundary is a separate question; see the correction above). Run `automaticum task pin -repo <checkout> --write <suite>/<task>`, which rebuilds the artefact and writes its new `sha256`. Then run `automaticum oracle verify -repo <checkout> <suite>/<task>`; every fixture must come out `ok` on each of its 3 runs. Tasks are read at each run's start, so no reload is needed. A run never builds an artefact, though: the gate SKIPs a run whose pinned artefact is not built, or whose oracle was not proven for the task's current hash. Even a comment-only edit to `task.toml` changes the task hash. So run `oracle verify` on every installation before the next run there. Never move a lane host's checkout while a client's batch on that task is running or queued, because every queued run would be SKIPPED. Stage the binaries (`bin/*.new`), mail the client, and wait for their "go". On a lane host, a task-only change needs no binary swap and no daemon restart. Ask the client by mail to hold that task, then run a background script that polls `automaticum status` until it shows `0 queued` and no lane `running`. Have it refuse a dirty checkout, then run `git fetch && git checkout <sha>`, `oracle verify`, `config check` and `task show` (compare `hash` and the artefact `sha256` with the dev build), and mail DONE. `TestLoadAll` in `internal/task/task_test.go` asserts `manic_miner`'s version, so bump it there too. To see what the agent will read, run the built artefact directly. It is at `<data_root>/artefacts/<sha256>/<output>`, where `data_root` comes from the config's `automaticum.toml` (it is not always `<root>/data`). Run it with `docker run --rm --network none -v <artefact>:/r:ro -v <fixture>:/w/<file>:ro -w /w <oracle image> /r <file>`.

- **[gotcha]** Scripted edits can fail quietly in three ways. (1) `sed -i 's/old/new/'` exits 0 when nothing matches. A guessed pattern (for example assuming a call reads `f(wireCalls(reqs))`) changes nothing, and the next build shows the same error. Print the real line with `sed -n Np file` first, or use a Python `edit(path, [(old, new)])` helper that raises when `old` is missing. (2) A parameter or struct field you add can collide with a name already in scope: `v` was already the local verdict in `ingest.Canary`, and `editStreak` was already a counter field of the struggle state. Grep the function body and the struct before you choose the name. (3) Inserting an import with `sed '0,/^import (/s//...'` does nothing in a file that has no `import (` block (`internal/ingest/cap.go` had none), and the build then fails with `undefined: detect`. Check with `grep -n '^import' file`; if there is no block, add a single `import "..."` line after `package`.
- **[pattern]** When you change an exported function's signature, `go build` does not compile `_test.go` files, so it reports only the production callers. Run `go vet ./internal/<pkg>` (it type-checks the tests) on each package until it prints nothing about `not enough arguments`. Then run `go build ./internal/...` for the dependants (`detect` → `ingest` → `daemon`, `export`) and `CGO_ENABLED=0 go vet ./cmd/automaticum`. Where outside packages call the function and do not need the new argument, keep a thin wrapper with the old signature (`Spans(text, h)` → `SpansWith(text, h, nil)`).
- **[gotcha]** `go build ./...` from the repo root fails with `no required module provides package github.com/northwind/...`. The cause is `tasks/train-ml/*/checker/main.go`, whose imports resolve only inside each task's own seed module, so the failure is not your change. Compile-check the libraries with `go build ./internal/...` (cgo on). - **[gotcha]** Never match a served model by `/v1/models` `data[].id` alone. A llama-server started with several `--alias` values lists them all in `data[].aliases` and reports the first in sorted order as `id`, so a path alias (`/mnt/...gguf`) beats the tag. - **[pattern]** When a change moves a daemon default (what a route returns when a parameter is absent), have the CLI ask for the new default explicitly (for example `detect` sends `metric=*`). - **[convention]** In a daemon JSON answer, an opt-in block must never encode "not asked" the same way as "empty". The rules: no `omitempty` on it; an empty object when it was asked for and nothing matched; `null` only when it was not asked for; and a header field saying what was included. Prefer to make the useful data the default and let a flag narrow it. This comes from bug-094: `detect --json` left out `metrics` unless they were named, and a client's script read the missing block as zeros and divided by zero.
- **[convention]** Every number a detector or a measure decides with is a registered threshold (D148, owner 2026-11-12: "the thresholds comes from the SDK but as defaults. automaticum must be flexible"). Add a new one to the registry in `internal/detect/thresholds.go`. Give it an `Origin` (`sdk` when the SDK has the same rule, `owner` for an owner document or decision, `harness` when no owner decision is on record, which the owner must confirm), a `Source` naming exactly where the default comes from, and a `Doc`. The package constant stays as the registry's `Default`. In a function, read the value as a local at the top (`unitMin := o.T.Int(ThUnitMinChars)`, or `v.Int(...)` for a `Values` argument) so the body is unchanged; a nil `Values` gives every default. A constant used as an array length must become `make([]int, n+1)`. A count the code divides by or takes a modulo of gets `Min: 1`. Never read the bare constant. Call sites that have the installation at hand pass `d.thresholds()` or `opt.T` (ingest, detect, export, guard watch, canary), not nil. Each value is then overridable per installation (`[thresholds]` in `automaticum.toml`) and per read (`detect --threshold name=N`). Any output computed with it must carry the effective value and where it came from (sdk/owner default, config, cli), so results read at different thresholds are never merged unseen. If the SDK has no such rule, tell the client and ask the owner for the default; never invent one.
