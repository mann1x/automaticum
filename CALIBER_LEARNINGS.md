# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** When you add an arm field whose value can equal the SDK's own default, drop it from `Resolved()` in `internal/config/arm.go` at that value (as with the empty `stop_on`, `reasoning_history = "auto"`, `max_consecutive_trips = 3`), so existing arm ids and pooled runs are kept. Add a `Test...Identity` case (the default is absent from `Resolved()`, another value is present and changes the id). Then compare `automaticum arm show -repo . <arm>` ids from a `CGO_ENABLED=0` build of the new tree against one built after `git stash`.
- **[gotcha]** A Python heredoc sent through `ssh host '...'` with nested quotes (`'"'"'EOF'"'"'`, escaped `\"` in f-strings) fails with `SyntaxError: unexpected character after line continuation character`. Write the script to the session scratchpad, `scp` it to a work dir on the remote host, run `python3 <file> <args>`, then delete the work dir.
- **[pattern]** To test new analysis code (detectors, span placement, export) against real runs before deploying, read the raw blobs on the lane host. `automaticum run ls -json -limit 200` gives the ids. Then for each run, `automaticum logs -kind model_requests <run>` gives a tar of `run-<id>/<stem>.json` + `<stem>.response.json`, where each response body is the raw SSE stream, and `automaticum logs -kind events <run>` gives the JSONL event log (guard cuts are `notice` events with `metadata.verdict`). Build a throwaway probe with `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build` from a temp dir in the repo, and delete that dir right after building so it is never committed. `scp` the binary to a work dir on the lane host and loop it over the runs there; the daemon does not need a restart.
- **[pattern]** Never restart the lane host's daemon under a client's running batch. Stage the new binaries beside the old ones (`bin/automaticum.new`, `bin/automaticumd.new`). Gate the swap in the same ssh command on `automaticum status` showing `^0 queued` and `lane-1 ... idle` (if not, `NOT IDLE; exit 1`), then `systemctl stop automaticumd`, `mv` the binaries, `git checkout` the commit in the host's repo and `systemctl start`. If a client is mid-batch, mail them not to queue anything and run a background watcher that polls every 5 min. Confirm with the client's exact command plus `-dry-run`.
- **[gotcha]** `automaticum export conversations` (`GET /v1/runs/{id}/export`) exports only finished runs of training tasks (`training = true`, D105) that are not INVALID and were started with `-capture-requests`. It refuses the others (403 / 422 / 404) and names them as passed over. So a batch meant for training traces must be started with `-capture-requests`; the capture cannot be added after the run. `--batch` takes a glob (`'k-pool-*'`), and a run's directory in `--out` must not exist yet.
- **[gotcha]** The SDK guard's `verdict.chars` counts UTF-16 code units (JavaScript length), while Go `[]rune` offsets count code points. Convert before slicing a captured field, or a non-BMP character before the loop shifts every span by one. The `short_unit_repeat` detector returns the leftmost repeating unit, which may start with a space (`" abc"` rather than `"abc "`), so derive test expectations from that.
- **[gotcha]** `claude-hooks-res` resource names (`bs2/build`, `bs2/gpu0`, ...) use the private host nickname, which the privacy gate flags. In `.wolf/memory.md` rows, commit messages and other tracked notes, write "the blackswan-2 build claim" instead of the resource id, or the commit stops `NOT CLEAN [.wolf/memory.md]`. Use the resource ids only in the `claude-hooks-res` commands themselves.
- **[pattern]** A commit that changes anything under `runner/` (e.g. a protocol bump) needs every lane image rebuilt on the lane host after the binaries are swapped. Claim the host's build resource, `automaticum lane drain lane-1`, run `automaticum image build base` first, then `for l in typescript python go rust cpp dotnet; do automaticum image build $l; done`. Check that the new runner is inside: `docker run --rm --entrypoint grep automaticum-lane:python -c "PROTOCOL = <n>" /opt/automaticum/runner/runner.mjs` should print 1. Then `automaticum lane resume lane-1`, run a stub smoke run, and release the claim.

It must also listen where the stub endpoint points (the bridge gateway, `-listen 172.17.0.1:7412` per `endpoints/stub.toml`). Start it detached with a cap, `(timeout 300 automaticum stub serve -script <f> -listen 172.17.0.1:7412 > <log> 2>&1 &)`, and check `curl -s http://172.17.0.1:7412/api/version` before `run start -arm stub-sdk-<ver> -task demo/answer`. When done, `pkill -f` the server and delete the script.

- **[gotcha]** The pre-commit privacy grep must pass file names NUL-separated and fail closed: `hits=$(git ls-files -z | grep -zv -e CALIBER_LEARNINGS.md -e package-lock.json -e '^tasks/train-sh/' | xargs -0 grep -IlniE "$P" 2>&1); rc=$?`. Then run the same over `git ls-files -z tasks/train-sh` with a narrower pattern `$R` of real path fragments instead of the bare top-level server directory, because the sample data there legitimately has made-up server paths and `10.0.0.x`. Commit only when the output is empty and `rc` is 1 or 123 (through `xargs` a clean grep exits 123). Any other `rc`, or any error line, means stop. After committing and before pushing, check the committed tree too: `git grep -IlniE "$P" HEAD -- . ':!CALIBER_LEARNINGS.md' ':!**/package-lock.json' ':!tasks/train-sh/'` must print nothing with rc 1. A plain `if grep ...; then NOT CLEAN; else commit` reads grep's exit 2 as clean, and that let a real path out in a pushed commit. The grep also reads your own words, including old `.wolf/memory.md` rows. Never write the gate's patterns or any real path fragment into a tracked note (cerebrum, anatomy, memory, commit message), not even a note about the gate; write "made-up server paths" instead. Reword and rerun; do not widen the exclusions.
- **[gotcha]** `claude-hooks-res` resource names (`bs2/build`, `bs2/gpu0`, ...) use the private host nickname, which the privacy gate flags. - **[gotcha]** solidPC's `grep` is ugrep. A context or bounded-repeat grep like `grep -o ".\{0,1200\}needle.\{0,300\}"` on a minified SDK bundle or a session `.jsonl` transcript fails with `exceeds complexity limits`. Slice with Python instead: `s.find("needle")` or `re.finditer`, then print `s[i-160:i+260]`. For transcripts, `json.loads` each line and walk `message.content[].input.command`. The installed SDK sources are under `<SPIKE_ROOT>/m2/sdk/<version>/node_modules/@cerebriline/*/dist/` (`agents`, `core`, `shared`). The `.d.ts` files hold the hook and option types (`shared/dist/agents/types.d.ts`, `core/dist/types/config.d.ts`).
- **[fix]** `automaticum sdk add -repo . <ver>` fails with `docker: 400: create runner/sdk/<ver>: "runner/sdk/<ver>" includes invalid characters for a local volume name`. Docker reads a relative bind path as a volume name. Pass an absolute checkout: `automaticum sdk add -repo "$PWD" <ver>`, and the same for `sdk verify`.
- **[pattern]** To provision a new SDK release from npm, follow the `learned-new-sdk-release` skill. In short: write `runner/sdk/<ver>/package.json` and generate its lockfile in the pinned `NodeImage` (`internal/sdk/sdk.go`) with `npm install --package-lock-only --ignore-scripts`. Then write `sdk.toml` (`version`, `source = "registry"`) and run `sdk add -repo "$PWD"`, which writes `bundle_sha256` into `sdk.toml`; commit that. Run `sdk verify` next. Before you claim a fix landed, check that the bundle really carries it. Then add `arms/stub-sdk-<ver>.toml`.
- **[pattern]** To find which SDK releases support an option or hook, loop over every installed build instead of reading just one: `for v in <SPIKE_ROOT>/m2/sdk/*/; do grep -o '<symbol>' $v/node_modules/@cerebriline/{agents,core}/dist/index.js | wc -l; done`. Check `core` separately from `agents`, because the agent can read a config field that core never forwards. For example, `onReasoningLoopLimitReached` was dropped by core in 4.100.250–262 and forwarded from 4.100.266 (X9).
- **[gotcha]** The SDK's `reasoning_loop` guard ends a run by itself after `maxConsecutiveTrips` consecutive cut turns. The default is 3; the notice reads "Ending the run after 3 turns cut for this", phase `aborted`. Since D108 every arm states `guards.reasoning_loop.max_consecutive_trips` (base 3). The runner answers `onReasoningLoopLimitReached` with `stop` only when `stop_on` names `reasoning_loop.aborted` or the whole guard. SDK core up to 4.100.262 drops the host's hook, so a run the SDK ends against the arm becomes `INVALID` (`guard_limit_breach`). 4.100.266 forwards the hook, and its `cut`/`aborted` notices carry `maxConsecutiveTrips`, which the runner also checks against the arm. Do not pick another limit number yourself; that is the owner's call.
- **[pattern]** Changing an arm's `[harness] sdk_release` (or any resolved field) changes its id, so its runs no longer pool with the old ones. Before and after the change, check `automaticum arm validate -repo . <arm>` and `automaticum arm show -repo . <arm> | grep ^id` from a `CGO_ENABLED=0` build. Record the move in the arm's header comment: who decided it, the date, and old id → new id. Make the switch only on the owner's go.

- **[pattern]** A run's wall and idle limits are the lower of the arm's and the task's, so an arm can never lengthen a task's cap. To lengthen it, give the batch its own limits (D107), e.g. to retry TIMEOUT runs at 50 min. Use `automaticum run start ... -wall-s 3000 [-idle-s S]`, a campaign batch's `wall_s` / `idle_s`, or `automaticum batch limits -wall-s S <batch>` for runs still queued; the run in flight keeps its limits. The run records the batch that owns it, and the basis's "agent settings" fact names that batch, so such runs never pool with task-cap runs. Never bump a task's version just to change its wall limit.
- **[gotcha]** Since D107, `automaticum run start` takes `-task` several times and `-suite <suite>` (every task of that suite once). One batch then interleaves across the tasks, each in its own lane image, and the answer lists `images` per task. A campaign `[[batch]]` takes `tasks`, `suites`, `capture_requests`, `wall_s` and `idle_s`. A binary older than D107 has only the single `-task`, so check `automaticum run start -h` on the lane host before mailing a client a multi-task command. CLI flags go before positionals.
