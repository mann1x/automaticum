# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** When a detector's counting rule changes, measure its threshold again on the new count; never carry the old maximum over. For `duplicate_definitions`, keying definitions by class moved the limit from 3 to 1. Update the canary test's expected numbers with a comment giving old → new. Add positive and negative controls in `controls.go`. Bump `detect.Version` (library) and `AnalysisVersion`. Then check with `CGO_ENABLED=0 go run ./cmd/automaticum detect --self-test`.
- **[pattern]** To end a run from the daemon with a particular verdict, cancel the flight's context with a typed cause (`context.WithCancelCause`, like `run.GuardStop`). Then add an `errors.As` case to the "What ended it" switch in `internal/run/run.go`, which sets `Facts`; `Decide` in `verdict.go` maps those facts to the verdict. Test it like `TestOperatorAbortAndEndpointChange`: `newWorld`, with the fake runner calling `cancel(cause)`.
- **[gotcha]** In the private-name scan, `git ls-files -z | xargs -0 grep -Il ...` exits with **123** when nothing matches, not 1, because xargs reports 123 when any grep call returned 1. So `rc=123` on the tracked-files grep means clean. A plain `git diff --cached | grep` still gives `rc=1` for clean. Read the two codes separately.
- **[gotcha]** A finding that ingest writes itself (not a `detect` library detector) needs an entry in two maps in `internal/ingest/analyse.go`: `Versions`, for its version, and `owned`, so that a re-ingest replaces its old rows. A new blob kind is not read by analysis until `ingest.Load` has a `ref.Kind == "<kind>"` branch for it. List the kind in 020 §2 too.
- **[pattern]** Types shared by the verdict and the analysis (such as `run.Held` and `run.SlotSample`) belong in `internal/run`. `internal/ingest` may import `internal/run`, but `internal/run` must never import `internal/ingest`, because that would be an import cycle. Before moving a type, check with `grep -rn automaticum/internal/ingest internal/run/`.
- **[pattern]** A client may relay an owner decision that contradicts an existing decision. For example, "FAIL with oracle, like a guard stop" contradicts D99, under which a guard stop is FAIL whatever the oracle says. Do not pick one reading. Ask the owner directly with AskUserQuestion, name both readings and the conflict, and record the answer as the D-row before you build it.
- **[pattern]** To end a run from the daemon with a particular verdict, cancel the flight's context with a typed cause (`context.WithCancelCause`, like `run.GuardStop`). Then add an `errors.As` case to the "What ended it" switch in `internal/run/run.go`, which sets `Facts`; `Decide` in `verdict.go` maps those facts to the verdict. A new verdict fact must also be read back in `recorded()` in `internal/run/rescore.go`, so that `Rescore` and `Redecide` decide stored runs the same way. Keep its proof in the run's provenance. An operator correction to a stored run follows `handleInvalidate`: keep `PriorVerdict`, support `?dry_run=1`, then call `ingest.Run`.
- **[gotcha]** When a client asks automaticum to wait longer before a server is "presumed dead", or to change any timeout or abort, first check whether the code is the pinned SDK's. automaticum runs the SDK unpatched. `OpencotiServerSilentError` ("sent nothing for 595s") comes from a fixed 600,000 ms silence ceiling in `@cerebriline/llms` `dist/providers.js`, and no setting changes it. Get the arm's release from `run show` ("SDK release") and grep that release's provisioned bundle. Search for literal strings (`sent nothing for`, `=600000`), not minified names: the identifiers differ between releases (`jI` in 4.100.269, `VI` in 4.100.266), and a regex on one release's names fails silently on another.
- **[gotcha]** llama-server's `GET /slots` is at the server root, not under `/v1`, so trim the endpoint's `base_url` suffix `/v1`. On the opencoti build the top-level `n_decoded` is null. The count is in `next_token[0].n_decoded`, a list of one entry per sequence; older builds have an object there. Read both shapes. Ollama has no `/slots`.
- **[gotcha]** `go build ./...` on the host fails, because some packages need the cgo link image. So does `go test ./cmd/automaticum` without `CGO_ENABLED=0`: it fails with `collect2: error: ld returned 1 exit status` and `[build failed]`, which looks like a code error. To check that the code compiles, run `go build ./internal/... && CGO_ENABLED=0 go build -o /dev/null ./cmd/automaticum`, then `go vet` on the package you changed. Always test the CLI as `CGO_ENABLED=0 go test ./cmd/automaticum`.
- **[gotcha]** `go build` does not compile `_test.go` files, so a changed function signature still builds while its tests are broken. After you add a parameter, find the callers in tests with `grep -rn '<Func>(' --include=*_test.go internal/` and run `go vet <pkg>`, which does compile the tests. A `sed` that adds an argument of another package's type (such as `detect.Options{}`) also needs that package's import in the test file, or vet fails.
- **[pattern]** The repetition guard is evaluated in four places, and a rule change must reach all of them with the same options: the analysis (`repetitionGuard` in `internal/ingest/repguard.go`, options from `DetectOptions(r)`), `detect` (`internal/daemon/detect.go`, `ingest.DetectOptions(m.Run)`), the live stop watcher (`watchGuard`, started in `internal/daemon/daemon.go` with `detect.RulesFor(arm.Harness.SDKRelease)` and `tk.Prompt`), and its control in `internal/detect/controls.go`. Find them with `grep -rn 'GuardText\|GuardFires(\|watchGuard(' --include=*.go .`.
- **[gotcha]** When a new rule fires on a run you counted as healthy, check how old that run's stored analysis is before you call it a false positive. Runs analysed before analysis version 17 have no wire-only answers, so a real loop the model wrote up to its output limit never appeared in their findings. In one case `run show` reported `reasoning_loop` 0 on such a run, while its wire capture held one progress line written to the output limit. Search the wire capture (`automaticum logs --kind wire <run>`) for the text, not `logs --render` or the event stream, which do not hold wire-only answers. The wire text is JSON-escaped several levels deep (`\\\\n`), so grep for a phrase that contains no newline or quote.
- **[gotcha]** On the lane host, `claude-hooks-res acquire <gpu>:exclusive` fails (`BUSY`) while any other session holds that GPU `:shared`, for example a client's gate. A daemon binary swap on an idle lane does not use the GPU, so take `<gpu>:shared` for it instead of waiting for exclusive. The idle check in the swap script (`lane-1 .* idle` and `0 queued`) is what protects the client's runs, not the claim.
- **[correction]** Before you tell a client (by mail) which config key to set, read `examples/config/automaticum.toml`, not the Go field path. The keys of `automaticum.toml` are top-level (`private_tasks = "<dir>"`). `config.Local.Daemon` is only the Go struct name; there is no `[daemon]` table. The loader refuses unknown fields (`unknown fields: daemon, daemon.private_tasks`), so wrong advice crash-looped `automaticumd` under systemd on the lane host (bug-080). There is no `config check` verb yet. `automaticum task ls` is not a validator either: `place.tasks()` in `cmd/automaticum/config_cmds.go` ignores a `config.LoadLocal` error.
- **[pattern]** Bumping the runner protocol touches four files. In `runner/runner.mjs`, change `const PROTOCOL`; in `internal/run/protocol.go`, change `const Protocol`, and the two must be equal. In `runner/PROTOCOL.md`, update the title, add a dated "Protocol N" paragraph that says why the number went up, add the new note to the runner-note list and rename the "What protocol N does not do" heading. In `.claude/rules/runner-protocol.md`, update "(currently N)". Hide a frequent keep-alive runner note (such as `receiving`) in `Renderer.Line` (`internal/ingest/render.go`), so that `run tail` and `logs --render` stay readable. The runner tests need no SDK: run `cd runner && node --test test/`.
- **[gotcha]** `human.Millis` and `human.Duration` print values under a minute in seconds: 900 ms prints as `0.9s` and 31000 ms as `31s`, never `900ms`. Write the CLI output a test expects from what the formatter actually returns, not from a guess.

- **[gotcha]** The CLI's flag parsing prints `flag provided but not defined: -X` on the **first** line, then the whole usage. Piping the output through `| tail` hides the error, and the run looks as if it printed only its usage. Read a failed CLI call with `2>&1 | head`. `run start` has no `--batch` flag: the batch id is generated and printed (`batch b<date>-<id>`).
- **[pattern]** In a new `cmd/automaticum` verb, return `errFailed` (`config_cmds.go`) to exit 1 after printing your own summary: `fail()` prints nothing for it. There is no `exitError` type. Other codes come from `exitCode` and from `apiErr`, which `exitOf` maps to 3, 6 or 7. To test a verb that needs a configuration, copy `examples/config` into `t.TempDir()` with `os.CopyFS`, rewrite `repo =` to the checkout (`filepath.Abs("../..")`) and `data_root =` to the temp dir, and write a 40-character `token` file. See `exampleConfig` in `check_cmds_test.go`.
- **[pattern]** To pin the artefact of a task you wrote, run `automaticum task pin --write <suite/task | dir>` (D140), with an empty `sha256 = ""` or no key at all. Do not build against 64 zeros and copy the sum out of the error message. A copy of the task can be pinned by its directory, so no task root has to change.

Read a failed CLI call with `2>&1 | head`. `run start` has no `--batch` flag: the batch id is generated and printed (`batch b<date>-<id>`). `logs` has no `--stderr`: what the runner wrote to stderr is `automaticum logs <run> --runner`. That is where you find a Node heap OOM behind `ABORTED` "the runner ended without its last line (exit code 134)". `run ls` prints fixed-width columns, and queued rows leave some empty, so awk `$(NF-k)` fails (`attempt to access field -2`). Use `cut -c` or `--json`.
- **[pattern]** On a monitoring tick on the lane host, work out who caused an unexpected change before you report it. Runs SKIPPED with "stopped by the operator before it started", drained lanes and daemon restarts are usually the client's own doing. Find them with `journalctl -u automaticumd | grep msg=change`, which logs the method, path and client for every stop, drain and `POST /v1/runs`. Check the restart count with `systemctl show automaticumd -p NRestarts`. To see whether a long run is still alive, compare `timeout 20 automaticum run tail <run> | grep '^── turn' | tail -1` between ticks. Report what you find; never stop or retry a client's runs yourself.
- **[pattern]** To remove a client's arms when the owner says so, first check what extends them: `grep -ln 'extends *= *"<arm>"' config/arms/*.toml`. Then move the files to `config/arms.removed-<YYYYMMDD>/` instead of deleting them, rerun `automaticum config check` (it should exit 0) and mail the client. Arms are read per run, so this needs no daemon restart, and stored runs of those arms stay as they are.
- **[gotcha]** A bug in an SDK tool (sed, awk, grep, read_files, timeouts) is fixed in the owner's own `@cerebriline/*` source, the cline monorepo beside this checkout, on its `main`. automaticum runs the SDK unpatched, so never work around it in the runner. In that repo, Vitest finds the tests only when run from `sdk/packages/core` with `bunx vitest run --config vitest.config.ts src/...`. From the repo root it says "No test files found". Pushing and tagging a release is outward-facing: ask the owner first, then follow the learned-new-sdk-release skill.
- **[gotcha]** For several minutes after a release tag publishes to npm, the registry's `dist-tags.latest` and `time[<ver>]` still show the old release. Check with `npm view @cerebriline/sdk@<ver> version` instead, and confirm the fix shipped by grepping the `npm pack`ed `core/dist/index.js` for a new string. The release-notes preview script (`generate-fork-changelog.mjs`) rewrites `apps/vscode/CHANGELOG.md`, so run `git checkout -- apps/vscode/CHANGELOG.md` before you push.
