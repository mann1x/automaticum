- **[gotcha]** The host's `python3` has no `tomllib` (`ModuleNotFoundError: No module named 'tomllib'`), so a script that reads `task.toml` files runs in the pinned Python 3.12 oracle image instead: write it to the scratch dir and `docker run --rm -v "$PWD/tasks:/r/tasks:ro" -v "<scratch>/scan.py:/s/scan.py:ro" python@sha256:<the digest the train tasks pin> python -I /s/scan.py`. The lane layers' and oracle images' `awk` is mawk 1.3.4, which silently matches nothing on interval expressions (`/a{3}/`), so a shell task or checker must not rely on them.
- **[gotcha]** Editing Go files with a Python `str.replace` heredoc breaks gofmt's struct-literal alignment (a key shorter than its neighbours needs two spaces, `Tmpfs:  map[...]`), and a `sed -i '0,/^import (/s//import (\n\t"fmt"/'` puts the new import first instead of in sorted order: run `gofmt -l internal` after such edits and `gofmt -w` whatever it names before `go vet` and `make test`, or the commit carries unformatted Go.
- **[pattern]** Verify a new lane layer as the lane uses it, not as root: `docker run --rm --network none --user 1000:1000 --tmpfs /workspace:exec,uid=1000,gid=1000 --tmpfs /tmp:exec,mode=1777 -e HOME=/tmp --entrypoint sh automaticum-lane:<layer> -c 'cd /workspace && node -e "console.log(process.version)" && test -f /opt/automaticum/runner/runner.mjs && ldconfig -p | grep -c libatomic.so.1 && <compile and run a hello program, then the toolchain's test runner>'`. A toolchain that writes to a home (dotnet, cargo) wants `export HOME=$(mktemp -d /tmp/home-XXXXXX)` inside the container, because the runner gives each run a fresh home under tmpdir (`runner.mjs`); the dotnet layer sets `DOTNET_CLI_USE_MSBUILD_SERVER=0 MSBUILDDISABLENODEREUSE=1` so no MSBuild node outlives a build in the lane. Every layer must print the base's Node (22.23.3, so `.ts` runs with type stripping on by default), find the runner and at least one `libatomic.so.1`. Go and Cargo are set offline in their layers (`GOPROXY=off GOTOOLCHAIN=local`, `CARGO_NET_OFFLINE=true`), so a check that fetches a module or crate is a layer error, not a network one. Record each built layer in `docs/specs/063-suite-multi-language.md` §2 "As built", `.wolf/anatomy.md` and the CLAUDE.md layout line.

- **[gotcha]** `automaticum run start` takes one `-task` per batch, so a pool over N tasks is N batches queued one after another on the lane, not interleaved; reordering the loop sets the queue order. Only a campaign `[[batch]]` (`tasks = [...]`, `runs = n`) interleaves across tasks, and campaigns have no `capture_requests` yet. A batch whose runs are training material therefore uses the `run start` loop with `-capture-requests`. CLI flags go before positionals.
- **[gotcha]** Judge a loop run from the whole wire, not its first requests: count reasoning chars per turn. In `<data_root>/runs/<id>/out/wire.jsonl` a chat row's `response_body` is the raw SSE stream. Keep the `data: {` lines, `json.loads` each, concatenate `choices[].delta.reasoning_content`, `.content` and `.tool_calls` per request, and take the last `finish_reason` (`None` on a cut turn). A tools-less request with `reasoning_budget_tokens: 0` and `finish_reason: stop` is the SDK's forced rewrite after a cut, not the arm's setting. While the run is in flight, the runner's trips are in the lane container's stdout: `docker logs <container> | grep '"note":"guard_trip"'` gives rows with `guard`, `phase`, `cause`, `iteration` and `message`. A bounded `timeout 15 ./bin/automaticum run tail <id> > <work>/tail.txt` carries the same rows from the moment it attached.
- **[gotcha]** The runner's `guard_trip` note keeps only `guard`, `phase`, `cause`, `iteration` and `message`. The guard's exact judgement is only in the SDK's own `notice` event, read with `automaticum logs -json <id> | grep reasoning_loop`. Its `metadata.verdict` is `{kind (e.g. line-cycle), period, cycles, chars, sample}`, plus `consecutiveTrips` and `channel`. The response the guard cut is the capture's `*.response.json` with `complete: false` just before the notice's timestamp, and its reasoning length equals `verdict.chars` exactly. Use these two together to locate a cut span without re-running a detector.

- **[gotcha]** On the host, `go build ./internal/... ./cmd/automaticum/` ends with `link: running gcc failed: exit status 1` for `cmd/automaticum`. - **[gotcha]** A task fixture in a Go test must be a complete task. A hand-written `task.toml` with only `id`, `suite`, `version`, `layers` and `prompt` fails `Load` with `exactly one oracle must be primary; 0 are`.
  - Copy `tasks/demo/answer` instead (`os.CopyFS`) under `<tmp>/<suite>/<task>`, rewrite the `id =` and `suite =` lines, and insert extra keys after `version = 1`.
  - A new `[[fixture]]` needs a name the demo task does not already use, or `Load` fails with `fixture "<name>": name missing, malformed or repeated`.
  - A signature change to `task.Find`/`task.LoadAll` also touches `internal/gate/gate_test.go` and `internal/run/run_test.go`. Find the callers with `grep -rn 'task.Find(\|task.LoadAll(' --include=*_test.go internal cmd`.
- **[gotcha]** The private tasks root (D105, `private_tasks` in the local configuration's `[daemon]`) is read by the daemon beside the repository's `tasks/`. - **[convention]** Every container sandbox mounts `/tmp` as a tmpfs with `exec`: the artefact build and oracle in `internal/task/exec.go`, the lane in `internal/run/run.go`, the SDK install in `internal/sdk/sdk.go`. `grep -rn 'Tmpfs' --include=*.go internal` finds every spec; keep them in step when changing isolation.
- **[correction]** "Looping" in the Gemma loop test means the SDK's `reasoning_loop` guard, phase `cut`, cause `reasoning_loop`: the reasoning repeated a block and the SDK cut the request (a notice ending "Cutting the request and continuing.").
  - The same guard fires with cause `answer_loop` or `argument_loop`, and reaches phase `aborted` at `reasoningLoopDetection.maxConsecutiveTrips`.
  - `loop_detection` is a different guard: consecutive identical tool calls, soft on the 2nd, hard on the 5th. Its soft trips are not a loop.
  - The post-hoc detector library (`detector.reasoning_loop.*`, `reasoning_repetition`, `runaway`) can read 0 on runs where the guard cut several times, so never infer "no loops" from detector metrics alone.
  - Report guards by name, phase and cause with counts (`run show -json <id>` metrics `guard_trips.<guard>.<phase>.<cause>` and `guard_stop.*`; `metrics` may be a list or a map), never as "loops".
