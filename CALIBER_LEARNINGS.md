# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** Before you change a lane host's `config/arms/base.toml` default release, find which client arms actually follow it. `grep '^sdk_release'` undercounts, because an arm that states no release can still inherit one from the client's own templates (on blackswan-2, 42 arms state none, yet only `stub` follows base). Resolve every arm with the staged CLI: `for f in *.toml; do a=${f%.toml}; [ "$a" = base ] && continue; automaticum arm show -repo <repo> -json $a | python3 -c 'import json,sys; print(json.load(sys.stdin)["harness"]["sdk_release"])'; done | sort | uniq -c`. Name the arms that move in the go request. Run `bin/automaticum.new config check --repo <repo>` with the staged binary before the swap, and `config reload --dry-run` after the host config edit.
- **[gotcha]** On blackswan-2, unattended-upgrades runs needrestart. On 2026-11-14 it restarted automaticumd, containerd, docker, ollama and xollama at once. The journal showed a clean drain with `NRestarts=0`, and the restart command was in `/var/log/apt/history.log`. When a daemon shows an unexpected start, check apt history and needrestart before you suspect a crash or a client. Since 2026-11-15 the owner has excluded those units ("yes, add automaticumd too") in `/etc/needrestart/conf.d/90-*.conf` and `91-no-autorestart-automaticumd.conf` (`$nrconf{override_rc}{qr(^automaticumd\.service$)} = 0;`). After an upgrade they keep running the old binaries, listed as pending by `needrestart -b -r l`, until someone restarts them deliberately with the lanes idle.
- **[gotcha]** `node --test` (the runner tests, `cd runner && node --test test/`) prints its summary as `ℹ pass 56` / `ℹ fail 0`, not TAP's `# pass`. A `grep -E '^# (pass|fail)'` matches nothing and makes the whole command exit 1, so grep `'^ℹ (pass|fail)'` or read `| tail -10`. Run it and `make test` as separate commands: chained, the grep's exit status hid the `make test` result. Send `make test` output to a log, print `rc=$?`, then grep the log for `^(FAIL|---)`. Likewise, a background command that ends in `grep -c <pattern> log` exits 1 when the count is 0, which is the good case, so the task is reported as failed although the build succeeded. End such commands with `; true`, or print the count with `echo`.
- **[gotcha]** In the private-name scan, `git ls-files -z | xargs -0 grep -Il ...` exits with **123** when nothing matches, not 1, because xargs reports 123 when any grep call returned 1. So `rc=123` on the tracked-files grep means clean. A pipeline that ends in `cut`, `head` or `tail` reports that command's status. Simplest: use `grep -c -i -E "$P"` and read the count (0 = clean), on `git diff --cached | grep '^+' | grep -v 'registry.npmjs.org'` before the commit and on `git show HEAD` after it. To stage without the hook churn files, use `git add -A -- . ':!.wolf/cron-state.json' ':!.wolf/suggestions.json'`. Some hits are expected and are not leaks: npm lockfile `resolved` URLs, the scan patterns in `CALIBER_LEARNINGS.md` itself, and sample paths in the `tasks/train-sh` seeds and checkers. The `/shared/` pattern also catches prose that names the shared package followed by a slash and a path (its `dist` directory, for example), lists packages joined by slashes, or gives a source path that runs past `packages/shared`. Write "the shared package's dist/index.js" or "agents, shared and llms" instead. A hit in `CALIBER_LEARNINGS.md` after the commit hook has run needs `sed` plus `git commit --amend --no-edit --no-verify`. Absolute paths in Go test fixtures that look like host paths also hit the scan, so use neutral ones such as `/data/a` or `/opt/r`. `.wolf/memory.md` and `.wolf/buglog.json` are tracked, so their rows must use the neutral host names too: write "the blackswan-2 build claim", never the private resource name of a claim or GPU, and "the same artefact as the dev build", never the dev machine's name. Mailbox addresses (`<session>@<host>`) also carry the private host name, so write "the SDK owner (ollama)", not the address.
- **[correction]** Adopting a new `@cerebriline/sdk` release is not only pin, verify and default. On 2026-11-20 the owner said "we missed the prompt template integration so far, big mistake". Before you map a release onto existing behaviour, list what it adds for a host and decide for each item whether the runner, the arm config or ingest must take it up. Quick way: per package (`shared`, `core`, `llms`, `agents`), collect the names in `export{...}` of `dist/index.js` in both builds and print the added and removed ones; then read `git log v<old>..v<new>` and `git diff --stat v<old> v<new> -- sdk/packages` in the SDK repo. A diff of string literals between two minified bundles is useless: identifier renames give thousands of hits. Check that a new export is really called at runtime with `grep -c <name>` over core, agents and sdk `dist/index.js` (an export used only by the extension's settings changes nothing in a run). Report new features to the owner instead of writing "no behaviour change".
- **[correction]** A task version that changes verdicts is a comparability boundary used from then on; do not plan or propose a rescore of earlier runs unless the owner asks (owner, 2026-11-19: "we do not rescore for v6, we use it from now going forward"). - **[pattern]** Before you ask a client for a deploy window on a lane host when the change touches arm resolution or identity, stage the binaries as `.new` and compare every arm id with the old and the staged CLI: `for f in <config>/arms/*.toml; do n=$(basename $f .toml); o=$(bin/automaticum arm show $n | awk '/^id/{print $2}'); w=$(bin/automaticum.new arm show $n | awk '/^id/{print $2}'); [ "$o" = "$w" ] && echo same $n || echo CHANGES $n; done`. Say in the request which arms change id (on 2026-11-19: 46 client arms the same, 19 `stub*` changed). For the staged `config check`, use a temporary `git worktree add --detach` of the new commit and remove it after. During the window: take the blackswan-2 build claim (shared) with `claude-hooks-res acquire` even when the client's go came by mail (the client asked for it), mail START and DONE, and leave the client's GPU claims and processes alone. A runner protocol bump means every lane image must be rebuilt on the host (`automaticum image build -repo <repo>`, about 7 to 8 minutes for 11 images: run it in the background) before any run; a run on an old image is SKIPPED.
- **[convention]** A runner protocol bump touches: `const PROTOCOL` in `runner/runner.mjs` and `const Protocol` in `internal/run/protocol.go` (they must be equal), the title, a new `**Protocol N (date):**` paragraph and the "What protocol N does not do" heading in `runner/PROTOCOL.md`, the numbers in `.claude/rules/runner-protocol.md`, and 040. A new ingest finding needs: its constant, an entry in `Versions` and in the `owned` map in `internal/ingest/analyse.go` (a finding not in `owned` is not replaced on reanalyse), an `AnalysisVersion` bump, a `findingLine` case in `cmd/automaticum/client_cmds.go`, the "From analysis version N" note in 070 §2, and a `D` row. New facts from a runner note are read in `internal/ingest/events.go` (`eventLine` field, `Events` field, a `case` on the note name); test with `ReadEvents` on literal JSON lines and also with a bare `&Events{}`.
- **[gotcha]** A multi-file edit written as one Python script with `assert old in s` per replacement writes the files before the failing assert and skips the rest (on 2026-11-20 the specs were written, `runner/PROTOCOL.md` and the rules file were not). After an `AssertionError`, run `git diff --stat` on the target files to see which were written, and rerun only the missing ones. A common cause: an earlier `replace` in the same script changed the text a later anchor needed (a heading renamed before it was used as the anchor).
- **[pattern]** To probe the SDK's exports or one tool alone, mount the build root (`<data_root>/sdk/<ver>`, which holds `node_modules`) with `--network none -v <build>:/s:ro -w /s` and import by package name, or by absolute path as long as the path runs through a directory named `node_modules`. Mounting `node_modules` itself as `/n` and importing `/n/@cerebriline/sdk/dist/index.js` fails with `ERR_MODULE_NOT_FOUND ... @cerebriline/core`. A probe script inside the lane image must sit at `/opt/automaticum/runner/<probe>.mjs`, next to the mounted `node_modules`. On the dev machine a quick probe also runs with the host's `node <probe>.mjs $SPIKE_ROOT/m2/sdk/<ver>` importing `root + "/node_modules/@cerebriline/sdk/dist/index.js"`. Some functions are exported only by `@cerebriline/shared` and not re-exported by the main SDK package (`renderPromptTemplate`, `isOllamaNativeProvider`, `shadowPromptTemplates`, `resolvePromptTemplate`, `validatePromptTemplate`), so the runner imports `@cerebriline/shared` itself. To find which pinned releases have a function, loop over `$SPIKE_ROOT/m2/sdk/*/node_modules/@cerebriline/core/dist` and grep its `.d.ts` files for `export declare function <name>(`, then confirm at runtime by checking `m[name] === undefined` on the imported module per release. Never look for a build with `find /`: it ran into the 2-minute timeout. Anything that starts Chrome (the browser, `render_image`, `transform_image`) also needs `-e HOME=/tmp --tmpfs /tmp:exec` with `--user 1000:1000`. Print the tools' input schemas this way (`sdk.BROWSER_TOOL_INPUT_SCHEMA` etc.) before you write stub turns, rather than guessing argument names.
- **[pattern]** To read an SDK function's real implementation in the minified bundle (`<node_modules>/@cerebriline/core/dist/index.js`), find its local name from the export list with the regex `(\w+) as createEditorDiagnosticsHooks\b`. The export is written `Kmt as createEditorDiagnosticsHooks`, so `createX as (\w+)` finds nothing. Then print from `s.find('function ' + name + '(')`. A string unique to the function (an imported helper such as `readDeclaredFamily`) also leads to its body. The type declarations under `dist/**/*.d.ts` (`grep -rl <name> --include=*.d.ts`; shared's are under `dist/prompt/`, core's under `dist/extensions/`) give the option names to pass, and their doc comments often explain the behaviour. `diff` the same `.d.ts` between two builds to see what a release added.

It expects the CLI at `am` in the same directory (rebuild it there first), reads the job's `protocol` from `const PROTOCOL` in the repo's `runner/runner.mjs`, and runs the stub arm in the variants `auto`, `custom`, `nope` (must exit 3, refused) and `disabled`; each variant's notes are in `<variant>/runner.jsonl`. Read it with `ip -4 addr show docker0`; never hard-code it. `chown -R 1000:1000` the workspace and out first, because rust-analyzer's `cargo check` reports nothing on a root-owned directory.
