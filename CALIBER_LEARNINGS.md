- **[gotcha]** When a new rule fires on a run you counted as healthy, check how old that run's stored analysis is before you call it a false positive. Runs analysed before analysis version 17 have no wire-only answers, so a real loop the model wrote up to its output limit never appeared in their findings. In one case `run show` reported `reasoning_loop` 0 on such a run, while its wire capture held one progress line written to the output limit. Search the wire capture (`automaticum logs --kind wire <run>`) for the text, not `logs --render` or the event stream, which do not hold wire-only answers. In the wire capture each newline is escaped several levels deep (a run of backslashes before the `n`), so grep for a phrase that contains no newline or quote.
- **[gotcha]** In the private-name scan, `git ls-files -z | xargs -0 grep -Il ...` exits with **123** when nothing matches, not 1, because xargs reports 123 when any grep call returned 1. So `rc=123` on the tracked-files grep means clean. A plain `git diff --cached | grep` still gives `rc=1` for clean. Read the two codes separately. Some hits are expected and are not leaks: npm lockfile `resolved` URLs (`@cerebriline/shared/-/shared-<v>.tgz`, so filter `registry.npmjs.org/` out of the staged diff), this file's own scan patterns, and sample paths in the `tasks/train-sh` seeds and checkers. `.wolf/memory.md` and `.wolf/buglog.json` are tracked, so their rows must use the neutral host names too: write "the blackswan-2 build claim", never the private resource name of a claim or GPU. Mailbox addresses (`<session>@<host>`) also carry the private host name, so write "the SDK owner (ollama)", not the address.
- **[gotcha]** Arm names may not contain `+`. `internal/config/arm.go` refuses them (`"stub-sdk-4.100.275+da478ecc8a" is not a valid arm name`). One bad file in `examples/config/arms/` makes every arm unreadable, so `make test` fails far from the cause: `TestGates` in `internal/daemon` reports "the arms cannot be read", and `TestDetectRuns` panics with a nil pointer dereference. For a local SDK build named `<release>+<commit>`, name the arm file `stub-sdk-<release>.toml` and put `+<commit>` only in `[harness] sdk_release`. Before `make test`, check a new arm with `AUTOMATICUM_CONFIG=$PWD/examples/config <tmp>/am arm validate <arm>`.
- **[pattern]** If a release's npm publish did not run, pin it as a local build (D68). The directory is `runner/sdk/<release>+<commit>/`. Its `sdk.toml` says `source = "local"`, gives the `commit`, and gives the packs' own prerelease `version` (`<release>-g<commit>`), not the bare release. The packed `.tgz` files go to `automaticum sdk add --packs <dir>`. Keep the packs in gitignored `docs/local/`, never in a tracked path or in /tmp. The `package.json` overrides and the lockfile step are in the learned-new-sdk-release skill.
- **[pattern]** When you hand audit findings to someone else (the SDK owner or a client), write out every item in full in the findings file. Each item needs file:line at a named commit, what is wrong, whether it was reproduced or only reasoned, the repro path, and the expected text. Never fold minor items into labels such as "bash m1-m7" or "N2". Labels cost two extra mail rounds, and for one label the recipient fixed a different text from the one the audit meant.
- **[gotcha]** Any code that compares SDK releases must read a local build's version. An arm says `4.100.275+<commit>`, and the package and the run record say `4.100.275-g<commit>`. Splitting on `.` and calling `Atoi` reads both as an unknown release, so `detect.RulesFor` quietly fell back to the 4.100.250 rules (bug-084). Use `releaseAtLeast` in `internal/detect/guards258.go`, which drops everything from the first `+` or `-`, and put both spellings in the test table.
- **[pattern]** Before you adopt an SDK release, diff every guard automaticum replays between the release tags in the cline monorepo: `git log --oneline v<old>..v<new> -- sdk/packages/core/src/runtime/safety/loop-detection.ts`, then `git show v<new>:<path>`. A rule that changed needs five things. First, a release-gated rule set (`CallGuardFor`, `RulesFor`) carried in `detect.Options` and set from the run's release in `ingest.DetectOptions`. Second, a bump of `detect.Version`, so that stored findings are recomputed. Third, a `**Library version N (date).**` entry at the top of the list in 070 §3, with the spec's `**Status:**` line bumped. Fourth, a test that pins the old and the new answer on the same calls. Fifth, every place that builds options, which `grep -rn 'detect.Options{' --include=*.go internal cmd` finds (the imported-run path in `internal/ingest/analyse.go` passes empty options).
- **[pattern]** Installing a pinned SDK build on a lane host needs no binary swap and no daemon restart. The steps: take the host's build claim, mail the client START, fast-forward the repo checkout, and copy the packs and check them with `sha256sum -c SHA256SUMS`. Then run `automaticum sdk add -repo <repo> -packs <dir> <build>` and `automaticum sdk verify -repo <repo> <build>`. Copy the stub arm into the host's `config/arms/`, run one stub smoke run on an idle lane, release the claim and mail DONE. The CLI takes single-dash Go flags (`-repo`, `-packs`, `-limit`). The full steps are in the learned-new-sdk-release skill.
- **[pattern]** For a quiet full run of the host tests, use `make test 2>&1 | grep -E '^(ok|FAIL|---|panic)' | grep -v '^ok'; echo rc=${PIPESTATUS[0]}`. No output and `rc=0` mean every package passed.
- **[correction]** Before you tell a client (by mail) which config key to set, read `examples/config/automaticum.toml`, not the Go field path. The keys of `automaticum.toml` are top-level (`private_tasks = "<dir>"`). `config.Local.Daemon` is only the Go struct name; there is no `[daemon]` table. The loader refuses unknown fields (`unknown fields: daemon, daemon.private_tasks`), so wrong advice crash-looped `automaticumd` under systemd on the lane host (bug-080). `automaticum task ls` is not a validator: `place.tasks()` in `cmd/automaticum/config_cmds.go` ignores a `config.LoadLocal` error. Since D141, run `automaticum config check --config <dir>` before any restart or reload, and tell clients to do the same. It exits 1 and names each problem.
- **[correction]** The owner expects the basics of a long-running service to be built without being asked (2026-11-09: "do I have to specify even the most basic things?"). That means live configuration reload (SIGHUP, an API/CLI verb, a directory watch), validation before any swap with the old config kept whole on error, full signal handling taken at the first moment of start-up (SIGPIPE ignored, SIGUSR1/2 diagnostics), graceful drain, a panic isolated to the one run or loop it hit, and a status that says what still waits for a restart. When a daemon feature touches configuration or lifecycle, design for "nothing stops unless it truly must" from the start.
- **[pattern]** Since D144, a change to `automaticum.toml`, `lanes/`, `endpoints/` or the token files takes effect without a restart. The daemon watches its directory (`watch_config`, on by default); `systemctl reload automaticumd` (SIGHUP) or `automaticum config reload [--dry-run]` apply it at once. Never restart a lane host's daemon just to add a lane or endpoint. Check the result with `automaticum config show`, which shows the last reload and why it was refused, if it was. Only `data_root`, `archive_root`, `docker_socket` and `repo` need a restart; they are listed under `restart`. A host still on a build from before D144 needs the binary swap first. Code that reads `config.Local` in the daemon must go through `Lane`/`LaneNames`/`Endpoint`/`MayUse`/`Settings`, never the maps.
- **[pattern]** In a new `cmd/automaticum` verb, return `errFailed` (`config_cmds.go`) to exit 1 after printing your own summary: `fail()` prints nothing for it. There is no `exitError` type. Other codes come from `exitCode` and from `apiErr`, which `exitOf` maps to 3, 6 or 7. A verb that talks to the daemon gets its client from `addClient`, which reads only `automaticum.toml` (`config.LoadClient`), so a broken lane file cannot keep the CLI from the daemon. Never call `p.local()` (full `LoadLocal`) just to reach the daemon. - **[pattern]** On a monitoring tick on the lane host, work out who caused an unexpected change before you report it. Runs SKIPPED with "stopped by the operator before it started", drained lanes and daemon restarts are usually the client's own doing. Find them with `journalctl -u automaticumd | grep msg=change`, which logs the method, path and client for every stop, drain, config reload and `POST /v1/runs`. Check the restart count with `systemctl show automaticumd -p NRestarts`. To see whether a long run is still alive, compare `timeout 20 automaticum run tail <run> | grep '^── turn' | tail -1` between ticks. Report what you find; never stop or retry a client's runs yourself.
- **[gotcha]** `go build ./...` from the repo root fails with `no required module provides package github.com/northwind/...`. The cause is `tasks/train-ml/*/checker/main.go`, whose imports resolve only inside each task's own seed module, so the failure is not your change. Build and vet the application with `go build ./internal/... ./cmd/...` (and `CGO_ENABLED=0 go vet ./cmd/automaticum`), and check formatting with `gofmt -l internal cmd`.
- **[gotcha]** Always pass the cache root as a literal: `make build SPIKE_ROOT=<dir>`. In `SPIKE_ROOT=<dir> make build SPIKE_ROOT=$SPIKE_ROOT`, the shell expands `$SPIKE_ROOT` before the assignment, so make gets an empty value. The Makefile then mounts `/cache/gomod`, `/cache/gobuild` and so on, which creates a stray root-owned `/cache` tree on the host. The build still succeeds and hides the mistake. If `/cache` appears, delete it (after you check that it holds only the build caches).
- **[gotcha]** If you edit Go source with `python3 - <<'EOF'` and a plain `'''...'''` string, a Go escape written as `\n` becomes a real newline in the file. That splits the Go string literal, and the next `go vet` fails with no clear message. Write `\\n` inside the Python string, or use `r'''...'''`. Run `gofmt -l` right after each scripted edit, and look at broken lines with `sed -n A,Bp file | cat -A`.
- **[pattern]** For a daemon change (signals, reload, API), unit tests are not enough. Also run the real binary on a scratch configuration. Build with `make build SPIKE_ROOT=<dir>`. Then write a scratch config dir: copy `examples/config/arms` and `models`, add your own `lanes/` and `endpoints/`, a 40-character `token` with mode 0600, a small `free_floor_gb`, and `listen` on a spare loopback port such as `127.0.0.1:17411` so it does not clash with a local daemon. Start `bin/automaticumd --config <scratch>` in the background and drive it with `AUTOMATICUM_CONFIG=<scratch> bin/automaticum ...` and `kill -HUP/-USR1/-USR2/-TERM <pid>`. This found a CLI bug the Go tests missed. For Go tests that change the configuration under a serving daemon, use `liveRig(t)` in `internal/daemon/reload_test.go`.
- **[correction]** Keep `.wolf/memory.md` to actions that did something (owner, 2026-11-09). Never append a row for a monitoring or mail tick that changed nothing ("no mail, nothing to do", "waiting"). Log a tick only when it acted: a deploy, a mail answered, a failure found. To clean the file, drop rows whose action starts with `tick` and the empty `## Session: ... > Consolidated session (0 actions)` blocks the OpenWolf daemon leaves (there were about 450 of them). - **[gotcha]** Build the deploy binary **after** `git commit`. A binary built from the working tree before the commit labels itself `<previous sha>-dirty` in `automaticum version`, `status` and the daemon log. The host then reports the old commit for every check until the next deploy, and the DONE mail has to explain it. The order is: commit, `make build SPIKE_ROOT=<dir>`, `./bin/automaticum version` (it must show the new sha), then stage.
- **[pattern]** Before the idle-gated swap on a lane host, check the host's live configuration with the **staged** CLI: `AUTOMATICUM_CONFIG=<root>/config <root>/bin/automaticum.new config check --repo <root>/repo`. This catches any client arm, model, lane or endpoint file the new build refuses while the old daemon is still serving, so a failed check costs nothing. It also lets the START mail say that the client's configuration already passes.
- **[gotcha]** Lane-host units installed before D144 have no `ExecReload`, so `systemctl reload automaticumd` fails on them. Check with `grep -n ExecReload /etc/systemd/system/automaticumd.service`. Add it inside the swap script: back up the unit as `.pre-<sha>`, then `sed -i "/^ExecStart=/a ExecReload=/bin/kill -HUP \$MAINPID"`, escaping the `$` so the remote shell leaves it alone. Run `systemctl daemon-reload` before `start`. When you edit the unit before `systemctl stop`, systemd warns "unit file ... changed on disk"; that warning is expected and harmless. To verify, run `systemctl reload automaticumd`, then `journalctl -u automaticumd | grep reload`, which should show `configuration reloaded: nothing changed` with `source=signal`.
- **[correction]** automaticum must be usable as a tool by people and by assistants alike (owner, 2026-11-09: listing the running arms is "an incredibly basic command" and was missing, "again a very sloppy job"). Before you call a list or filter done, ask two questions. Can someone see what is running right now, by this noun? Does the filter cover runs in every state? A run's record (`arm_id`, model, verdict) is written only when the run finishes. Queued and running runs come only from `State.Queue` and `d.flights`, so a filter that reads only the record silently drops a batch in flight. Either match runs that have not finished (a running run has the arm it started with, a queued run the arm it would start with now) or say plainly what the filter leaves out. Every list needs `--json` output.

- **[pattern]** To test a daemon list or filter over runs in flight, hold the fake runner. Under `g.runner.mu`, set `g.runner.hold = make(chan struct{})` and `g.runner.started = make(chan string, 4)`. Start the runs and read `<-g.runner.started` to get the one now running. Make your assertions, then `close(g.runner.hold)` and call `g.waitFinished` on each run. Use `liveRig(t)` and `write(t, dir, ...)` to change an arm file while runs are in flight. `g.call(method, path, body, out)` calls `t.Fatalf` when the reply does not decode into `out`. So for an expected 4xx, pass `nil` as `out` and check only the status code.

- **[correction]** When a selector has a known blind spot, close it in the same change. Do not explain the gap or offer to fix it (owner, 2026-11-09: "add -arm-name too, of course, I mean, it's not obvious it's needed?"). An arm's id is a hash of its resolved content. Two arms that resolve alike, such as a gate arm identical to a probe arm, share an id, so `-arm` and `-arm-id` count each other's runs. Any filter by content identity therefore needs a filter by name beside it (`run ls -arm-name`, `?arm=`, `--where arm=`). Never end a report or a client mail by describing an obvious missing completion; build it.
- **[pattern]** Adding a field to `store.RunFilter` touches six places. (1) `where()` in `internal/store/duck/duck.go`. (2) The `memState.ListRuns` mirror in `internal/daemon/daemon_test.go`: without it, daemon tests silently ignore the new filter. (3) In `internal/daemon/api.go`, the `/v1/runs` query parse and the filter over the views of queued and running runs. (4) `whereFilter` and its "there are ..." error text. (5) The `--where` help strings in `cmd/automaticum/client_cmds.go` and `report_cmds.go`. (6) 090 §1. The daemon test rig's `fakeRunner` must write what a real record holds; it now sets `Arm: req.Arm.Resolved()`. If a daemon test expects an outcome a real record never gives, such as a retry refused because the record names no arm, the fake rig is wrong, not the code.
