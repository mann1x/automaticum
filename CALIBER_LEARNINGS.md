- **[pattern]** Before acting on a peer's claim about how a served template renders, reproduce it on the server itself. POST the exact message shape with `tools` and `chat_template_kwargs` to the opencoti server's root `/apply-template` and print the tail of the returned `prompt` from the last `<|turn>model`. - **[gotcha]** On the host, `go build ./internal/... ./cmd/automaticum/` ends with `link: running gcc failed: exit status 1` for `cmd/automaticum`. That is the DuckDB cgo link, which only works in the build containers, not a code error. Compile errors in `internal/...` still print before it, so read those first. For the CLI use `CGO_ENABLED=0 go build ./cmd/automaticum/` or `go vet ./cmd/automaticum/`, and `make build SPIKE_ROOT=<dir>` for the real binaries.
- **[gotcha]** A task fixture in a Go test must be a complete task. A hand-written `task.toml` with only `id`, `suite`, `version`, `layers` and `prompt` fails `Load` with `exactly one oracle must be primary; 0 are`.
- **[gotcha]** The private tasks root (D105, `private_tasks` in the local configuration's `[daemon]`) is read by the daemon beside the repository's `tasks/`. The CLI's `task ls`, `task show`, `task build`, `oracle verify` and `cell run` only see it when `AUTOMATICUM_CONFIG` names the config directory; without it a private task looks missing. Every task there must say `private = true` with a `canary` of 16 characters or more. The same `<suite>/<task>` in both roots is a load error for the whole set.

- **[pattern]** A run's wall and idle limits are the lower of the arm's and the task's, so an arm can never lengthen a task's cap. To lengthen it (e.g. retry TIMEOUT runs at 50 min), give the batch its own limits (D107): `automaticum run start ... -wall-s 3000 [-idle-s S]`, a campaign batch's `wall_s` / `idle_s`, or `automaticum batch limits -wall-s S <batch>` for runs still queued (the run in flight keeps its limits). The run records the owner `batch` and the basis's "agent settings" fact names it, so such runs never pool with task-cap runs. Never bump a task's version just to change its wall limit.

- **[pattern]** To test new analysis code (detectors, span placement, export) against real runs before deploying, read the raw blobs on the lane host: `automaticum run ls -json -limit 200` for the ids, then per run `automaticum logs -kind model_requests <run>` (a tar of `run-<id>/<stem>.json` + `<stem>.response.json`, each response body the raw SSE stream) and `automaticum logs -kind events <run>` (JSONL event log; guard cuts are `notice` events with `metadata.verdict`). Build a throwaway probe with `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build` from a temp dir in the repo, delete that dir right after building so it is never committed, `scp` the binary to a work dir on the lane host and loop it over the runs there; nothing needs the daemon restarted.
- **[gotcha]** `automaticum export conversations` (`GET /v1/runs/{id}/export`) only exports finished runs of training tasks (`training = true`, D105) that are not INVALID and were started with `-capture-requests`; others are refused (403 / 422 / 404) and the command names them as passed over. So a batch meant for training traces must be started with `-capture-requests` — it cannot be added after the run. `--batch` takes a glob (`'k-pool-*'`), and a run's directory in `--out` must not exist yet.
- **[gotcha]** The SDK guard's `verdict.chars` counts UTF-16 code units (JavaScript length), while Go `[]rune` offsets count code points; convert before slicing a captured field, or a non-BMP character before the loop shifts every span by one. The `short_unit_repeat` detector returns the leftmost repeating unit, which may start with a space (`" abc"` rather than `"abc "`), so derive test expectations from that.
