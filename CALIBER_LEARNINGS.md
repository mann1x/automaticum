- **[gotcha]** On "check mail", call `mailbox-list` first (a deferred tool: load it with `ToolSearch` and `select:mcp__pgvector__mailbox-list`) and read the ids it prints. A `mailbox-read` of a guessed next id answered `No such message addressed to you`, because ids are shared by all sessions and the next number may be someone else's mail. Check the list again before answering the owner: three mails had arrived during one planning step. Load a mailbox tool's schema with `ToolSearch` before the first call of a session: a `mailbox-send` with guessed parameter names (`from_session`, `to_session`) was answered `No recipient given` and sent nothing; the recipient parameter is `to` (`"to": "<alias>@<host>"`), and the sender is implied.

Then run `AUTOMATICUM_REFERENCE=<path of loop_detect.py> AUTOMATICUM_BLOCKS=<work>/blocks.json CGO_ENABLED=0 go test ./internal/detect -run Reference -count=1 -v`. - **[pattern]** When the owner says another session needs the GPU now ("pause the lane"), pause rather than stop: `automaticum run pause <run in flight>` holds the run before its next model request and drops the model (D83), and the queued runs wait behind the held run, so arm counts stay equal and nothing is lost. After about a minute check that `status` shows the lane `paused`, that the daemon's log has `the endpoint dropped its models for the pause`, and that `GET <base_url>/api/ps` returns `{"models":[]}`; then mail the requesting session (times, model dropped, `/api/ps` result, "mail me when done") and `mailbox-ack` their original request pointing to that mail. Resume with `run resume <run>` only after their mail. Since 2026-10-14 `automaticum batch pause <batch>` does the same for a whole batch and `lane drain <lane>` lets the run in flight finish and starts nothing else. The older graceful route (`run stop` each queued run, let the run in flight finish, unload the last model with `POST <base_url>/api/generate` `{"model":"<tag>","keep_alive":0,"stream":false}`) is for when a pause is not wanted; either way start nothing on that endpoint until they mail that it is free, then check `/api/version` and `/api/ps`.
- **[pattern]** Go edits made by a `python3` replace script are followed in the same call by `gofmt -l internal cmd` and `go vet` of the touched packages: `gofmt -l` named the file twice in one session (run `gofmt -w <file>` and go on), and `go vet` caught a guessed name at once (`d.log undefined (type *Daemon has no field or method log, but does have field Log)`). Have the script assert that each anchor text is present before replacing (`assert a in s, (p, a)`), so that a missed anchor stops the call. A script that edits several files writes each one as it goes, so a failed assert in the third file leaves the first two edited: after a failed call, look at what was written (`git diff --stat`, `sed -n` on the spot) before running a corrected script, which must not repeat edits already applied (one such call left dead code in `cmd/automaticum/control_cmds.go` that took a further call to remove). In a call that also commits, make a non-empty `gofmt -l` stop the call (`test -z "$(gofmt -l internal cmd)" || exit 1`): a file it listed was committed and pushed anyway and needed a separate `gofmt` commit. Before each commit, grep the tracked files (`git ls-files | xargs grep -IlniE '<private host names|private paths|LAN address prefix>'`) and expect no match, since the repo is public.
- **[convention]** A daemon handler that refuses a request explains itself with `fail(w, <status>, "<reasons>")`, never with `reply(w, 409, <struct>)`: the CLI's `client.do()` turns every status of 400 or more into an error built from the body's `error` field only and drops the rest, so a struct of reasons answered with 409 reached the user as a bare `409 Conflict`. Put every reason into the message (sorted, joined with `; `). In `internal/daemon/daemon_test.go`, give each `g.call(...)` a fresh output value (`bc = BatchControl{}`): JSON decoding into a reused struct keeps fields the next answer leaves out (`omitempty`), and a test read the previous call's `InFlight` and failed on correct code.
- **[pattern]** A rebuilt `bin/automaticumd` is not the daemon that is running: after `make build`, check that it is idle (`automaticum status`), find it by its port (`ss -ltnpH 'sport = :7411'`, which gives the pid), send `kill -TERM`, wait in a bounded loop until `kill -0 <pid>` fails, start the new binary with `nohup ... >> <work>/automaticumd.log 2>&1 &`, and wait until `curl -sf http://127.0.0.1:7411/v1/status` answers before the next command; the log then shows `detector self-test passed` before `automaticumd is up`. Wait on the pid, never on the port: a restart that only waited until `ss` showed port 7411 free started the new daemon while the old one still held the store, and it exited at once (`Exit 1`, `automaticumd stops ... duck: open .../state.duckdb` in the log, then `the daemon does not answer; is automaticumd running?`); the same start a few seconds later worked. Foreground `sleep` is blocked in the agent's shell: pause inside such loops with `timeout 0.5 tail -f /dev/null`. The files of `runner/` are copied into the lane image, so a change there is live only after `automaticum image build` (check with `automaticum image ls`); like the daemon restart, do it only with the lane idle and the queue empty, never while a batch runs or a run is paused in flight (it would split the batch or abort its run): write and unit-test meanwhile, deploy after. After a change to the ingest code or a detector, run `automaticum reanalyse` (or `--run <id>`, `--batch <batch>`, `--imported`): it derives metrics, tool calls and findings again from the stored blobs and never touches raw material, and it prints how many runs were analysed and which failed. Since D73 it is no longer true that it leaves verdicts alone: it applies the endpoint rule (see the D73 entry above).
- **[convention]** A new command in `cmd/automaticum` is one entry in the `cmds` map of `main.go` under its `"<noun> <verb>"` key plus one line in the usage text (the one-word commands `status`, `logs`, `reanalyse`, `detect` and `doctor` are in the separate `one` map). Parse its flags with `args = parse(fs, args)`, not `fs.Parse(args)`: Go's `flag` stops at the first argument that is not a flag, so `automaticum oracle verify demo/answer -repeats 2` printed the usage error until the helper was used. A command that opens the store goes in `store_cgo.go` with a stub returning `errNoStore` in `store_nocgo.go`; a command that talks to the daemon goes in `client_cmds.go` and uses `addClient` (one that only posts to `/v1/runs/<id>/<verb>` is a single `runPost("<verb>", "<what was done>")` entry, as `run invalidate`, `run identify`, `run pause` and `run resume` are); a new group of commands gets its own `<noun>_cmds.go` (as `control_cmds.go` for `lane`, `batch` and `run retry`). A new or changed flag or verb also goes into the command list of `docs/specs/090-interfaces.md` section 1. A new pure-Go package is added to the `test` target of the `Makefile` (recipe lines start with a tab) and to the `make test` sentence in `CLAUDE.md`; a new binary gets its own `go build` line in the `build` target.
- **[pattern]** Pause inside a run (D77, D83) is built on the SDK's `beforeModel` hook in the same process: the daemon writes a file `hold` beside the job, the runner prints `held`, `holding` (once a minute) and `released` (with `held_ms`) notes, held time is taken out of the wall time and stops the wall and idle limits, and `automaticum run pause <run>` / `run resume <run>` drive it; the SDK has no pause call for the root session and the hook does not see the abort signal, so a hold must be released on abort. When wrapping an SDK hook in `runner/runner.mjs`, keep the hook already set (the prompt-template hooks set one) and call it after your own. To try pause without a GPU, copy a stub script with `delay_ms` on every turn (6,000 ms on each turn of the `demo/answer` fix script gives about 30 s), start `automaticum stub serve --listen <addr> --script <file>` in the background, `run start --arm stub-sdk-4.100.251 --task demo/answer`, `run pause` after a few seconds, `run resume` later, then read `automaticum logs <id> | grep '"note":"\(held\|released\)"'`, `provenance.held_ms` and `provenance.holds` in `run show <id> --json`, and the `wall` line of `run show` ("paused for ... more, which is not counted"). On the stub the daemon logs `the endpoint did not drop its model ... /api/generate gave status 404`: expected, the stub serves only chat; the unload step is tested only on a real Ollama or xOllama endpoint (it was, on 2026-10-14: `the endpoint dropped its models for the pause` within 2 s of the hold).

Send exact questions to the SDK's session by mailbox: is it supported, what is lost on resume, and from which release. Record the decision as a `D` row with the spec section, mirror it in `.wolf/cerebrum.md`, and build only the part that does not depend on the answer.
- **[correction]** A guard's thresholds come from the release tag of the SDK build under test, in the SDK's GitHub repository (paths `sdk/packages/agents/src/...` and `sdk/packages/core/src/...`). They do not come from the SDK's development checkout on this host, which is dirty and is not what releases are cut from. - **[correction]** If an Ollama or xOllama server can be asked or told something, automaticum asks or does it itself. (1) Unloading the other model before a run is the switch `unload_others = true` in the endpoint's file of the local configuration (D79). It is off unless set, and without it gate `free` leaves the second arm of an interleaved batch on two tags waiting. Check the switch and `GET <base_url>/api/ps` before queuing such a batch. - **[pattern]** Pause inside a run (D77, D83) is built on the SDK's `beforeModel` hook. The daemon writes a `hold` file beside the job. The runner prints `held`, `holding` and `released` notes, and held time is not counted in the wall or idle limits. It is driven by `automaticum run pause|resume <run>`. - **[pattern]** When another session needs the GPU now, pause rather than stop: `automaticum run pause <run in flight>` (or `batch pause <batch>`) holds the run and drops the model, and the queued runs wait. Check that `status` shows `paused`, that the log has `the endpoint dropped its models for the pause`, and that `/api/ps` returns `{"models":[]}`. Then mail the other session and `mailbox-ack` their request. When they mail that the GPU is free, check `/api/ps` again, then `run resume <run>` and ack their mail. `lane drain <lane>` lets the run in flight finish and starts nothing else. For a full stop instead of a pause, take each queued run off with `run stop <id>`. When the lane is idle, unload the last model with `POST /api/generate` `{"model":"<tag>","keep_alive":0,"stream":false}`.
- **[gotcha]** Read the wire capture of a finished run through the daemon: `curl -s http://127.0.0.1:7411/v1/runs/<id>/blobs/wire`. Leave out the `*_body` and `*_headers` fields when printing. The single failed request per run is usually the startup probe `POST /api/engine?...endpoint=tokenize`, which xOllama answers with 404. It is not a fault of the agent.
- **[gotcha]** The directory of a run in flight exists only while that run runs: `<data root>/m2/runs/<run id>/{job,out,workspace}`, and the live wire capture is `out/wire.jsonl` there. List that directory instead of searching: a `find / -maxdepth 6 -name <run id>` failed. Once the run ends the directory is gone, and its material is read through the daemon's blob API.
- **[gotcha]** `automaticum run tail <id>` never ends and replays the run's stream from the start (5,710 lines after 50 minutes). It carries only `"k":"event"` lines, not the runner's `held`/`released` notes. A long `timeout` wait followed by `run tail | grep` in one call failed with no output. Capture it bounded to a file on persistent disk and grep the file: `timeout 8 ./bin/automaticum run tail <id> > <work>/tail.jsonl; true`. A plain grep for `holding` also matches the model's reasoning text. Read runner notes with `automaticum logs <id>`, or look for the wire requests in the file.
- **[pattern]** A model's control tokens (`<|im_start|>`, `<|im_end|>`, and so on) come from its tokenizer, never from a hand list. Use `POST <base_url>/api/show` with `{"model":"<tag>","verbose":true}` and take the tokens in `model_info.tokenizer.ggml.tokens` whose `tokenizer.ggml.token_type` is 3. `<think>` and `<tool_call>` are type 4, not control tokens. The verbose answer is about 8 MB: write it under the persistent work directory, never /tmp, and delete it afterwards. In code, use `run.ControlTokens`. It loads nothing on the server.
- **[pattern]** A rebuilt `bin/automaticumd` is not the daemon that is running. To restart it:
  1. Check that it is idle with `automaticum status`.
  2. Find its pid with `ss -ltnpH 'sport = :7411'` and send `kill -TERM`.
  3. Wait in a bounded loop until `kill -0 <pid>` fails. Wait on the pid, not the port: a start after waiting only for the port failed with `duck: open .../state.duckdb`.
  4. Start the new binary with `nohup ... >> <work>/automaticumd.log 2>&1 &`, then wait for `curl -sf http://127.0.0.1:7411/v1/status`.
- **[convention]** A new command in `cmd/automaticum` is one entry in the `cmds` map of `main.go` (one-word commands go in `one`) plus one line of usage. Parse flags with `args = parse(fs, args)`, not `fs.Parse(args)`. Placement:

- **[gotcha]** On the host, `go build ./...` and plain `go run ./cmd/automaticum` fail at link (cgo store), and `cmd/automaticumd` cannot be built on the host at all. Iterate with `CGO_ENABLED=0 go vet|test` on the packages and `CGO_ENABLED=0 go run ./cmd/automaticum detect --self-test`, and leave full builds to `make build`. A control in `internal/detect/controls.go` lists every detector that fires on it, in `detect.Text` order. Write the text, read the `FIRED` column, then decide. Filler in tests must not be periodic.
- **[env]** Every command that talks to the daemon needs `AUTOMATICUM_CONFIG=<data dir>/config` (the path is in `docs/local/`). Without it the command answers `no configuration directory`. Use the built `./bin/automaticum`, not `go run`.
