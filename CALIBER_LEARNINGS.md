# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[fix]** `automaticum sdk add -repo . <ver>` fails with `docker: 400: create runner/sdk/<ver>: "runner/sdk/<ver>" includes invalid characters for a local volume name`. Docker reads a relative bind path as a volume name. Pass an absolute checkout: `automaticum sdk add -repo "$PWD" <ver>`, and the same for `sdk verify`.
- **[pattern]** To provision a new SDK release from npm, follow the `learned-new-sdk-release` skill. In short: write `runner/sdk/<ver>/package.json` and generate its lockfile in the pinned `NodeImage` (`internal/sdk/sdk.go`) with `npm install --package-lock-only --ignore-scripts`. Then write `sdk.toml` (`version`, `source = "registry"`) and run `sdk add -repo "$PWD"`, which writes `bundle_sha256` into `sdk.toml`; commit that. Run `sdk verify` next. Before you claim a fix landed, check that the bundle really carries it. Then add `arms/stub-sdk-<ver>.toml`.
- **[pattern]** To find which SDK releases support an option or hook, loop over every installed build instead of reading just one: `for v in <SPIKE_ROOT>/m2/sdk/*/; do grep -o '<symbol>' $v/node_modules/@cerebriline/{agents,core}/dist/index.js | wc -l; done`. Check `core` separately from `agents`, because the agent can read a config field that core never forwards. For example, `onReasoningLoopLimitReached` was dropped by core in 4.100.250–262 and forwarded from 4.100.266 (X9).
- **[gotcha]** The SDK's `reasoning_loop` guard ends a run by itself after `maxConsecutiveTrips` consecutive cut turns. The default is 3; the notice reads "Ending the run after 3 turns cut for this", phase `aborted`. Since D108 every arm states `guards.reasoning_loop.max_consecutive_trips` (base 3). The runner answers `onReasoningLoopLimitReached` with `stop` only when `stop_on` names `reasoning_loop.aborted` or the whole guard. SDK core up to 4.100.262 drops the host's hook, so a run the SDK ends against the arm becomes `INVALID` (`guard_limit_breach`). 4.100.266 forwards the hook, and its `cut`/`aborted` notices carry `maxConsecutiveTrips`, which the runner also checks against the arm. Do not pick another limit number yourself; that is the owner's call.
- **[pattern]** Changing an arm's `[harness] sdk_release` (or any resolved field) changes its id, so its runs no longer pool with the old ones. Before and after the change, check `automaticum arm validate -repo . <arm>` and `automaticum arm show -repo . <arm> | grep ^id` from a `CGO_ENABLED=0` build. Record the move in the arm's header comment: who decided it, the date, and old id → new id. Make the switch only on the owner's go.
- **[pattern]** When you add an arm field whose value can equal the SDK's own default, drop it from `Resolved()` in `internal/config/arm.go` at that value, as is done for the empty `stop_on`, `reasoning_history = "auto"` and `max_consecutive_trips = 3`. That keeps existing arm ids and pooled runs. Add a `Test...Identity` case: the default is absent from `Resolved()`, and another value is present and changes the id. Then compare `automaticum arm show` ids from the new tree against ids from a build made after `git stash`.
- **[pattern]** Never restart the lane host's daemon under a client's running batch. Stage the new binaries beside the old ones (`bin/automaticum.new`, `bin/automaticumd.new`). In the same ssh command, gate the swap on `automaticum status` showing `^0 queued` and `lane-1 ... idle`; if not, `echo NOT IDLE; exit 1`. Then `systemctl stop automaticumd`, `mv` the binaries, `git checkout` the commit in the host's repo and `systemctl start`. If a client is mid-batch, mail them not to queue anything and run a background watcher that polls every 5 min. Confirm with the client's exact command plus `-dry-run`.
- **[pattern]** A commit that changes anything under `runner/` (e.g. a protocol bump), or a new SDK build the lanes must use, needs every lane image rebuilt on the lane host after the binaries are swapped. Claim the host's build resource and run `automaticum lane drain lane-1`. Build `automaticum image build base` first, then `for l in typescript python go rust cpp dotnet; do automaticum image build $l; done`. Check that the new runner is inside: `docker run --rm --entrypoint grep automaticum-lane:python -c "PROTOCOL = <n>" /opt/automaticum/runner/runner.mjs` should print 1. Then run `automaticum lane resume lane-1`, do a stub smoke run, and release the claim.
- **[fix]** A stub smoke run that comes out `SKIPPED` with `gate model_tag: endpoint stub does not answer /api/version` means no stub server is listening. `automaticum stub serve` refuses to start without `-script <file>`: it prints only its usage line into your log and exits. It must also listen where the stub endpoint points: the bridge gateway, `-listen 172.17.0.1:7412` per `endpoints/stub.toml`. A working script for `demo/answer`: `{"model":"stub:latest","context_window":32768,"turns":[{"thinking":"set the number","tool_calls":[{"name":"run_commands","arguments":{"commands":["echo 'The answer is 42.' > answer.txt"]}}]},{"content":"answer.txt now says 42."}]}`. To trip the reasoning-loop guard, put several turns before it whose `thinking` repeats one sentence about 200 times. Start the server detached with a cap, `(timeout 300 automaticum stub serve -script <f> -listen 172.17.0.1:7412 > <log> 2>&1 &)`, and check `curl -s http://172.17.0.1:7412/api/version` before `run start -arm stub-sdk-<ver> -task demo/answer`. When done, `pkill -f` the server and delete the script.
- **[pattern]** To test new analysis code (detectors, span placement, export) against real runs before deploying, read the raw blobs on the lane host. `automaticum run ls -json -limit 200` gives the run ids. For each run, `automaticum logs -kind model_requests <run>` gives a tar of `run-<id>/<stem>.json` and `<stem>.response.json`, where each response body is the raw SSE stream. `automaticum logs -kind events <run>` gives the JSONL event log; guard cuts are `notice` events with `metadata.verdict`. Build a throwaway probe with `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build` from a temp dir in the repo, and delete that dir right after building so it is never committed. `scp` the binary or a Python checker script to a work dir on the lane host, run it there with `python3 -I`, and delete it afterwards. The daemon does not need a restart.
- **[gotcha]** `automaticum export conversations` (`GET /v1/runs/{id}/export`) exports only finished, non-INVALID runs of training tasks (`training = true`, D105) that were started with `-capture-requests`. It refuses the others (403 / 422 / 404) and names them as passed over. So a batch meant for training traces must be started with `-capture-requests`; the capture cannot be added after the run. `--batch` takes a glob (`'k-pool-*'`), and a run's directory in `--out` must not exist yet. To redo an export, write into a fresh `<dir>.new` and swap it in. omnimergekit's reader takes every `*.json` under `conversations/` that is not a `*.response.json` as a request, so nothing else may go there. Metadata goes beside it, as `*.jsonl` or under `runs/`. A run cut mid-request leaves one request with no response, and the reader must skip it.
- **[pattern]** A run's wall and idle limits are the lower of the arm's and the task's, so an arm can never lengthen a task's cap. To lengthen it, give the batch its own limits (D107), e.g. to retry TIMEOUT runs at 50 min. Use `automaticum run start ... -wall-s 3000 [-idle-s S]`, a campaign batch's `wall_s` / `idle_s`, or `automaticum batch limits -wall-s S <batch>` for runs still queued; the run in flight keeps its limits. The run records the batch that owns it, and the basis's "agent settings" fact names that batch, so such runs never pool with task-cap runs. Never bump a task's version just to change its wall limit.
- **[gotcha]** Since D107, `automaticum run start` takes `-task` several times and `-suite <suite>` (every task of that suite once). One batch then interleaves across the tasks, each in its own lane image, and the answer lists `images` per task. A campaign `[[batch]]` takes `tasks`, `suites`, `capture_requests`, `wall_s` and `idle_s`. A binary older than D107 has only the single `-task`, so check `automaticum run start -h` on the lane host before mailing a client a multi-task command. CLI flags go before positionals.
- **[gotcha]** A Python heredoc sent through `ssh host '...'` with nested quotes (`'"'"'EOF'"'"'`, escaped `\"` in f-strings) fails with `SyntaxError: unexpected character after line continuation character`. Write the script to the session scratchpad, `scp` it to a work dir on the remote host, run `python3 -I <file> <args>`, then delete it. For multi-line remote shell, `ssh host bash -s <<'EOF' ... EOF` with a quoted delimiter avoids the quoting.
- **[gotcha]** `TestCampaign` in `internal/daemon` sometimes fails under `make test` with a run of batch `k-c1-second` whose `Campaign` is `""` (bug-037, still open). It passes when rerun. Before you blame your change, rerun it alone with `go test -race -count=5 -run 'TestCampaign$' ./internal/daemon/`, then run `make test` again. If it shows up again, raise `occurrences` on bug-037 in the buglog rather than opening a new entry.

- **[gotcha]** An oracle proof is kept per installation and tied to the task as it is now. Verifying a new or changed task on linux-gpu-1 proves nothing on the lane host. Runs there come out `SKIPPED` with `gate oracle: the oracle of <task>, as the task is now, was not proven against its fixtures`. After deploying a commit that adds or changes a task, also run `automaticum oracle verify <suite>/<task>` on the lane host before telling a client to start. Once the static-gate change (bug-038) is deployed, `run start` (and `-dry-run`) answers 422 `nothing was queued: <arm> on <task>: gate <gate>: ...` when `oracle` or `harness_build` refuses. Fix the named gate (`oracle verify`, `sdk add`, `image build`); retrying the start changes nothing.
- **[gotcha]** `automaticum logs <run>` answers `run <id> has no events` while the run is still in flight. To watch a live run, use `timeout 10 automaticum run tail <run>` (it follows), and call `logs` only once `run show` has a `verdict` line. A wait loop for a stub run must allow more than the stub arm's 5-minute wall.

- **[gotcha]** The pre-commit privacy grep must pass file names NUL-separated and fail closed: `hits=$(git ls-files -z | grep -zv -e CALIBER_LEARNINGS.md -e package-lock.json -e '^tasks/train-sh/' | xargs -0 grep -IlniE "$P" 2>&1); rc=$?`. Then run the same over `git ls-files -z tasks/train-sh` with a narrower pattern `$R` of real path fragments instead of the bare top-level server directory, because the sample data there legitimately has made-up server paths and `10.0.0.x`. Commit only when the output is empty and `rc` is 1 or 123 (through `xargs` a clean grep exits 123). Any other `rc`, or any error line, means stop. After committing and before pushing, check the committed tree too: `git grep -IlniE "$P" HEAD -- . ':!CALIBER_LEARNINGS.md' ':!**/package-lock.json' ':!tasks/train-sh/'` must print nothing, with rc 1. A plain `if grep ...; then NOT CLEAN; else commit` reads grep's exit 2 as clean, and that let a real path out in a pushed commit. Never write the gate's patterns or any real path fragment into a tracked note (cerebrum, anatomy, memory, commit message), not even a note about the gate; write "made-up server paths" instead. Reword and rerun; do not widen the exclusions.
- **[gotcha]** The privacy gate also flags private host nicknames in your own notes. That covers the main host's name `solidPC` and the `claude-hooks-res` resource ids (`bs2/build`, `bs2/gpu0`, ...). It is easy to slip, because the global instructions and the mailbox use them. In `.wolf/cerebrum.md`, `.wolf/buglog.json`, `.wolf/memory.md` rows and commit messages, write the neutral names: `linux-gpu-1` for the main host that runs the daemon, `blackswan-2` for the lane host. Write "the blackswan-2 build claim" instead of the resource id. The mapping is in the untracked `docs/local/hosts.local.md`. If you don't, the commit stops `NOT CLEAN [.wolf/...]`. Use the resource ids only in the `claude-hooks-res` commands themselves.
