- **[gotcha]** On the lane host, `claude-hooks-res acquire <gpu>:exclusive` fails (`BUSY`) while any other session holds that GPU `:shared`, for example a client's gate. A daemon binary swap on an idle lane does not use the GPU, so take `<gpu>:shared` for it instead of waiting for exclusive. The idle check in the swap script (`lane-1 .* idle` and `0 queued`) is what protects the client's runs, not the claim.

The keys of `automaticum.toml` are top-level (`private_tasks = "<dir>"`). `config.Local.Daemon` is only the Go struct name; there is no `[daemon]` table. The loader refuses unknown fields (`unknown fields: daemon, daemon.private_tasks`), so wrong advice crash-looped `automaticumd` under systemd on the lane host (bug-080). - **[gotcha]** The CLI's flag parsing prints `flag provided but not defined: -X` on the **first** line, then the whole usage. Piping the output through `| tail` hides the error, and the run looks as if it printed only its usage. - **[pattern]** In a new `cmd/automaticum` verb, return `errFailed` (`config_cmds.go`) to exit 1 after printing your own summary: `fail()` prints nothing for it. There is no `exitError` type. - **[pattern]** On a monitoring tick on the lane host, work out who caused an unexpected change before you report it. Runs SKIPPED with "stopped by the operator before it started", drained lanes and daemon restarts are usually the client's own doing. Find them with `journalctl -u automaticumd | grep msg=change`, which logs the method, path and client for every stop, drain and `POST /v1/runs`. Check the restart count with `systemctl show automaticumd -p NRestarts`. To see whether a long run is still alive, compare `timeout 20 automaticum run tail <run> | grep '^── turn' | tail -1` between ticks. Report what you find; never stop or retry a client's runs yourself.
- **[pattern]** To remove a client's arms when the owner says so, first check what extends them: `grep -ln 'extends *= *"<arm>"' config/arms/*.toml`. Then move the files to `config/arms.removed-<YYYYMMDD>/` instead of deleting them, rerun `automaticum config check` (it should exit 0) and mail the client. Arms are read per run, so this needs no daemon restart, and stored runs of those arms stay as they are.

- **[gotcha]** When a new rule fires on a run you counted as healthy, check how old that run's stored analysis is before you call it a false positive. - **[gotcha]** Arm names may not contain `+`. `internal/config/arm.go` refuses them (`"stub-sdk-4.100.275+da478ecc8a" is not a valid arm name`). One bad file in `examples/config/arms/` makes every arm unreadable, so `make test` fails far from the cause: `TestGates` in `internal/daemon` reports "the arms cannot be read", and `TestDetectRuns` panics with a nil pointer dereference. For a local SDK build named `<release>+<commit>`, name the arm file `stub-sdk-<release>.toml` and put `+<commit>` only in `[harness] sdk_release`. - **[pattern]** If a release's npm publish did not run, pin it as a local build (D68). The directory is `runner/sdk/<release>+<commit>/`. Its `sdk.toml` says `source = "local"`, gives the `commit`, and gives the packs' own prerelease `version` (`<release>-g<commit>`), not the bare release. The packed `.tgz` files go to `automaticum sdk add --packs <dir>`. Keep the packs in gitignored `docs/local/`, never in a tracked path or in /tmp. The `package.json` overrides and the lockfile step are in the learned-new-sdk-release skill.
- **[pattern]** When you hand audit findings to someone else (the SDK owner or a client), write out every item in full in the findings file. Each item needs file:line at a named commit, what is wrong, whether it was reproduced or only reasoned, the repro path, and the expected text. Never fold minor items into labels such as "bash m1-m7" or "N2". Labels cost two extra mail rounds, and for one label the recipient fixed a different text from the one the audit meant.
- **[gotcha]** Any code that compares SDK releases must read a local build's version. An arm says `4.100.275+<commit>`, and the package and the run record say `4.100.275-g<commit>`. Splitting on `.` and calling `Atoi` reads both as an unknown release, so `detect.RulesFor` quietly fell back to the 4.100.250 rules (bug-084). Use `releaseAtLeast` in `internal/detect/guards258.go`, which drops everything from the first `+` or `-`, and put both spellings in the test table.
- **[pattern]** Before you adopt an SDK release, diff every guard automaticum replays between the release tags in the cline monorepo: `git log --oneline v<old>..v<new> -- sdk/packages/core/src/runtime/safety/loop-detection.ts`, then `git show v<new>:<path>`. A rule that changed needs five things. First, a release-gated rule set (`CallGuardFor`, `RulesFor`) carried in `detect.Options` and set from the run's release in `ingest.DetectOptions`. Second, a bump of `detect.Version`, so that stored findings are recomputed. Third, a `**Library version N (date).**` entry at the top of the list in 070 §3, with the spec's `**Status:**` line bumped. Fourth, a test that pins the old and the new answer on the same calls. Fifth, every place that builds options, which `grep -rn 'detect.Options{' --include=*.go internal cmd` finds (the imported-run path in `internal/ingest/analyse.go` passes empty options).
- **[pattern]** Installing a pinned SDK build on a lane host needs no binary swap and no daemon restart. The steps: take the host's build claim, mail the client START, fast-forward the repo checkout, and copy the packs and check them with `sha256sum -c SHA256SUMS`. Then run `automaticum sdk add -repo <repo> -packs <dir> <build>` and `automaticum sdk verify -repo <repo> <build>`. Copy the stub arm into the host's `config/arms/`, run one stub smoke run on an idle lane, release the claim and mail DONE. The CLI takes single-dash Go flags (`-repo`, `-packs`, `-limit`). The full steps are in the learned-new-sdk-release skill.
- **[pattern]** For a quiet full run of the host tests, use `make test 2>&1 | grep -E '^(ok|FAIL|---|panic)' | grep -v '^ok'; echo rc=${PIPESTATUS[0]}`. No output and `rc=0` mean every package passed.
