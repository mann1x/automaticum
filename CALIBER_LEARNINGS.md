- **[pattern]** For a daemon change (signals, reload, API, lists), unit tests are not enough. Also run the real binary on a scratch configuration. Build with `make build SPIKE_ROOT=<dir>`. Then write a scratch config dir: copy `examples/config/arms` and `models`, add your own `lanes/` and `endpoints/` (the stub endpoint is enough), a 40-character `token` with mode 0600, a small `free_floor_gb`, and `listen` on a spare loopback port such as `127.0.0.1:17411` so it does not clash with a local daemon. Start `bin/automaticumd --config <scratch>` in the background and drive it with `AUTOMATICUM_CONFIG=<scratch> bin/automaticum ...` and `kill -HUP/-USR1/-USR2/-TERM <pid>`. On a fresh scratch data root the gates refuse `run start`. For "sdk: not provisioned", symlink the provisioned `<data_root>/sdk` into `<scratch-data>/sdk`. For "the oracle ... was not proven", run `automaticum oracle verify demo/answer`. `run start` takes `-n <count>`, not `-count`. To test listings of queued runs, run `lane pause lane-1` before `run start`. Clear them afterwards with `batch abort <batch>`, then `kill -TERM`. This found CLI bugs the Go tests missed. For Go tests that change the configuration under a serving daemon, use `liveRig(t)` in `internal/daemon/reload_test.go`.
- **[correction]** When a selector has a known blind spot, close it in the same change. Do not explain the gap or offer to fix it (owner, 2026-11-09: "add -arm-name too, of course, I mean, it's not obvious it's needed?"). An arm's id is a hash of its resolved content. Two arms that resolve alike, such as a gate arm identical to a probe arm, share an id, so `-arm` and `-arm-id` count each other's runs. Any filter by content identity therefore needs a filter by name beside it (`run ls -arm-name`, `?arm=`, `--where arm=`). Never end a report or a client mail by describing an obvious missing completion; build it.

- **[gotcha]** Build the deploy binary **after** `git commit`. A binary built from the working tree before the commit labels itself `<previous sha>-dirty` in `automaticum version`, `status` and the daemon log. The host then reports the old commit for every check until the next deploy, and the DONE mail has to explain it. The order is: commit, `make build SPIKE_ROOT=<dir>`, `./bin/automaticum version` (it must show the new sha), then stage. A `<new sha>-dirty` label right after the commit is expected and harmless: the OpenWolf and Caliber hooks rewrite `.wolf/cron-state.json`, `memory.md` and similar files after every commit. Only the sha has to match.
