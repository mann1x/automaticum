# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[gotcha]** The daemon asks the gates before every run, and gate `oracle` refuses a task whose oracle is not proven for the task's current hash: a fresh data root, or any change to a file of a task, means `automaticum oracle verify <suite>/<task> --config <config dir>` must be run (again) for every such task before `run start`; it records the proof under the daemon's data root. Runs that end `SKIPPED` at once with a reason starting `gate <name>:` were refused by a gate, not by the runner: read `automaticum doctor`, do not look for the fault in the lane image or the runner.
- **[pattern]** Run `automaticum doctor --config <config dir>` (it needs the running daemon; `--lane`, `--arm` and `--task` narrow it, `--all` also lists the passes) after every restart of the daemon and before a `run start`: it exits non-zero when a gate refuses and names the command that mends it. `unchecked` for `gpu_ownership`, `server_log_level` and `expert` is expected until milestone 7, and for `gpu_residency` while the model is not loaded. Start the stub server before asking about the stub arm, since the gates ask the endpoint. A `wait` (the endpoint holds another model, D64) is not a failure: the run stays queued and is asked again every half minute, `automaticum status` prints `<lane> waits: <gate>: <reason>`, and `automaticum run stop <id>` takes it off. What the gates said for a run is under `provenance.gates` in `run show <id> --json`. No gate loads or unloads a model.
- **[gotcha]** In a Bash call of the shape `python3 - <<'EOF' ... EOF` with further commands on the lines after it, those lines run even when the script died: an edit of `docs/specs/110-acceptance-and-roadmap.md` stopped with `AssertionError` because it anchored on a `## 4.` heading the file does not have (the `grep -n '^## '` that would have shown it was in the same call), and the `git add -A` and the private-string check after it still ran and printed `CLEAN`. Print a file's headings in an earlier call than the script that anchors on them, never put `git add` or `git commit` in the same call as a scripted edit, and remember that a script editing several files writes each as it goes: after an assert fails midway, the earlier files are already changed and a plain re-run fails on their `assert old in s`. After scripted edits to Go files run `gofmt -w` on them: `gofmt -l` only names the file and exits 0, so the chain goes on with an unformatted file.
- **[gotcha]** In `internal/daemon/daemon_test.go`, `g.call("GET", "/v1/status", nil, &st)` into a `Status` that was used before keeps every field the new answer leaves out (`omitempty`): `TestGates` failed on a stale `Waiting` of a lane that was idle. Set `st = Status{}` before each call that decodes into a reused value, and run a test that depends on timers several times (`go test -race -count=3 ./internal/daemon/`) before trusting it.
- **[convention]** A finding that ingest writes on its own (`gpu_residency`, `model_reloaded`) needs, beyond its constant in `internal/ingest/analyse.go` and its entry in the `owned` map: a case in the switch of `cmd/automaticum/client_cmds.go` that prints findings in `run show`, a test in `internal/ingest/ingest_test.go` that injects the fault and one that shows the healthy case stays silent, a sentence in `docs/specs/070-diagnostics.md`, and an `**Open (O<n>)**` item when it is not decided whether the finding changes the verdict. Then `make test`, `make build`, restart the daemon, `automaticum reanalyse`, and read the new metric on the real runs (`automaticum run show <id> | grep -E '<metric>|<finding>'`). A milestone's state is written into 110 section 3 as a table of each acceptance-criterion item against what catches it and the named test that injects the fault, with what has no such test and what is carried forward said plainly in bold.
- **[correction]** Lane images hold no SDK (D66 to D68): the owner wants several SDK builds usable at the same time, the build an arm names provisioned at run time, and every build reproducible on demand. The SDK had been installed into the base image and named by an image label, so one image carried one SDK and a new release meant rebuilding images. Nothing that is a variable of an arm is baked into an image: an SDK build is a bundle installed once, pinned by hash and mounted read-only into the run's container, with the downloaded packages archived.
- **[pattern]** A new SDK build is a directory `runner/sdk/<build>/` (`<release>` for a published release, `<release>+<commit>` for a local build) with a `package.json` naming the SDK version, an `sdk.toml` (`version`, `source = "registry"`, or `"local"` with `commit`) and a `package-lock.json` written in the lane's Node image (`docker run --rm -v $PWD/runner/sdk/<build>:/def -v <dir>/cache/npm:/cache -e HOME=/tmp -w /def node@sha256:<digest> sh -c 'npm install --package-lock-only --ignore-scripts --no-audit --no-fund --cache /cache'`). Read the lockfile's `packages` map with a short `python3` script before installing (SDK version, the `zod` versions, whether `ollama-ai-provider-v2` is still there). Then run `automaticum sdk add <build> --config <config dir>` (`--packs <dir>` for a local build): the first install writes `bundle_sha256` into `sdk.toml`, which must be committed, since no run uses a build that is not pinned. Follow with `automaticum sdk verify <build>` (installs again with no network from the archived packages and compares the hash) and `automaticum sdk ls --deep`. An arm picks the build with `[harness] sdk_release`. Bundles live under the daemon's data root (about 470 MB each) and the archived packages under `archive_root`: a fresh data root needs `sdk add` for every build an arm names, and a run that ends `SKIPPED` with `the SDK release cannot be established`, or a refusing `harness_build` gate in `automaticum doctor`, means exactly that.
- **[gotcha]** `TestInstallRebuild` in `internal/sdk` runs real containers and is skipped unless `AUTOMATICUM_TEST_DIR` names a directory on a real disk that the container engine can mount (`AUTOMATICUM_TEST_DIR=<work>/tmp go test ./internal/sdk/`); `make test` alone does not exercise it. In `internal/run/run_test.go`, a new case in the table of `TestVerdicts` that gets past the checks before the run needs a runner function (with `nil` the fake engine panics with a nil pointer dereference), and `TestRecord` asserts the exact number of mounts of the run's container (`len(s.Mounts)`), so a new mount fails it until the count is raised. A new dependency of the executor or of the gates (such as `run.Bundles`) is wired in `cmd/automaticumd/main.go` for both the `run.Executor` and the gate input, and gets a fake in `internal/run/run_test.go` and in `internal/gate/gate_test.go`.
- **[gotcha]** The mailbox tools take `ids` as a list of numbers: `mailbox-read` with `[1249]` worked, `mailbox-ack` with the string `"[1249]"` failed with an empty answer. When a mail announces an SDK release, confirm it on the registry with a read-only request before acting on it (`curl -s https://registry.npmjs.org/@cerebriline%2fsdk`, then read `dist-tags.latest`, `time[<version>]` and the version's `dependencies`).
- **[gotcha]** The check for private strings before a commit (`git ls-files | grep -v -e CALIBER_LEARNINGS.md -e package-lock.json | xargs grep -IlniE '<private names and paths>' || echo CLEAN`) leaves out every `package-lock.json` (they are now under `runner/sdk/<build>/`), because registry URLs of packages named `shared` match the path pattern: a false positive. When the check names a file, look at the matching lines (`grep -n -iE ... <file> | cut -c1-160`) before deciding, and never skip the check. A note in `.wolf/cerebrum.md` that quoted the pattern literally made the check fail on the note itself: describe a pattern in words in tracked files.
- **[env]** The runner in `runner/` is Node and is never run on the host: test it in the digest-pinned Node image that `images/base/Dockerfile` starts from, with no network and the directory mounted read-only, `docker run --rm --network none -v $PWD/runner:/runner:ro -w /runner node@sha256:<digest of the FROM line> sh -c 'node --check runner.mjs && node --test 2>&1 | tail -12'`. Use `node --test` with no path: on the lane's Node 22, `node --test test/` takes the directory for one test file and reports `tests 1, fail 1`. Do not filter the test output down to pass and fail lines and chain the next step with `&&`: a call written that way came back with no output at all when the tests failed, so an empty result means a failure, not a pass. The tests of `wire.mjs` and `session.mjs` need no SDK, and `runner/package.json` names none: the SDK's manifest and lockfile are per build, in `runner/sdk/<build>/`. A lockfile is written in that same image, never on the host and never by hand, with an npm cache directory on a real disk and `npm install --package-lock-only --ignore-scripts --no-audit --no-fund`. Use the Node release of the lane image for it: a first lockfile written under a newer Node printed `EBADENGINE` warnings and was written again. When the SDK release cannot be established, `node runner.mjs <job.json>` prints one `end` line with outcome `refused` and exits 3; that is the gate working, not a fault. Keep the state line of `runner/PROTOCOL.md` in step with what has and has not been run against the SDK.

- **[pattern]** The first real runs of a new arm go in two steps. Ask every gate (`automaticum arm validate`, `automaticum arm diff <old> <new>`, `automaticum doctor --arm <arm> --task <suite>/<task> --all`), then queue one run with `automaticum run start --arm <arm> --task <suite>/<task> --idempotency-key <key>`: the flag is `--idempotency-key` (`--key` printed `flag provided but not defined`), and repeating the command with the same key starts nothing new. While that run is in flight, read its first agent request from the live wire file under the daemon's data root (`runs/<id>/out/wire.jsonl`: wait in a bounded loop until a line holds `"tools`, then print `think`, `options` and the server's `think_budget` from the last `"done":true` line of `response_body`). Only when the request carries what the arm states, queue the rest with `-n <count>` and a second key, and wait for them with a bounded waiter script outside the repo, run as a background call. The command line can be rebuilt with `make build` and used while a run is in flight, but the daemon is not restarted until the lane is idle, so runs already queued are still made by the old daemon.
- **[correction]** Durations are always written as hours, minutes and seconds (`8m 13s`, `1h 02m 05s`), never as bare seconds or milliseconds: the owner said so after a status report with a wall-time column of `493s`, `852s` and `1121s`, and wants proper human-readable formats in the command line, the terminal interface and the web interface (D69, 090 §1.1). - **[correction]** Every run must record where and on what it ran: the owner called it very important that a run says the inference point, the model family and variant ("Qwen 3.6 27B", "OmniMerge v4"), the GPU, the host and the sampling parameters. - **[gotcha]** A method added to the `store.State` interface compiles everywhere, because the test stores embed the interface (`memState` in `internal/daemon/daemon_test.go`, `memory` in `internal/ingest/ingest_test.go`), and then fails at run time with `panic: ... nil pointer dereference` in a frame marked `<autogenerated>` as soon as production code calls it: `go vet` is clean and only `go test` shows it. After adding one, implement it in `internal/store/duck/duck.go` (a new table means a higher `SchemaVersion` and a `CREATE TABLE IF NOT EXISTS` under a comment with the version), add it to every fake on the path that now calls it, and run both `make test` and `make test-store SPIKE_ROOT=<dir>`. The same holds when existing code starts calling a method the fake never had: ingest now calls `UpsertRun`, so `memory` got one. `ReplaceFindings`, `ReplaceToolCalls` and `ReplaceMetrics` replace all rows of a run: ingest keeps the findings of detectors it does not write through the `owned` map in `internal/ingest/analyse.go`, so a new detector that ingest writes must be added to that map or its old findings pile up beside the new ones.
- **[pattern]** A rebuilt `bin/automaticumd` is not the daemon that is running: after `make build`, check that it is idle (`automaticum status`), find it by its port (`ss -ltnpH 'sport = :7411'`, which gives the pid), send `kill -TERM`, wait in a bounded loop until `kill -0 <pid>` fails, start the new binary with `nohup ... >> <work>/automaticumd.log 2>&1 &`, and wait until `curl -sf http://127.0.0.1:7411/v1/status` answers before the next command; the log then shows `detector self-test passed` before `automaticumd is up`. Wait on the pid, never on the port: a restart that only waited until `ss` showed port 7411 free started the new daemon while the old one still held the store, and it exited at once (`Exit 1`, `automaticumd stops ... duck: open .../state.duckdb` in the log, then `the daemon does not answer; is automaticumd running?`); the same start a few seconds later worked. Foreground `sleep` is blocked in the agent's shell: pause inside such loops with `timeout 0.5 tail -f /dev/null`. After a change to the ingest code or a detector, run `automaticum reanalyse` (or `--run <id>`, `--batch <batch>`, `--imported`): it derives metrics, tool calls and findings again from the stored blobs and never touches raw material, and it prints how many runs were analysed and which failed. Since D73 it is no longer true that it leaves verdicts alone: it applies the endpoint rule (see the D73 entry below).
